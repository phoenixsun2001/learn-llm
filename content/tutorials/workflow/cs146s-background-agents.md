# 后台 Agent：异步委派与并行集群（CS146S Week 8）

CS146S 进入第四层「规模化与组织化」（Week 8–10）。本周的变化是**交互范式的**：前几周的 Agent 都在前台——你提问、它回答、你盯着它干活；后台 Agent 把关系倒过来——**你委派任务，Agent 在云端异步执行，完成后以 PR 的形式回来找你**。

一个人同时驾驭多个 Agent，从「不可能盯着」变成「认真评审 N 路产出」——瓶颈从编码能力变成**评审带宽与任务规格能力**。

## 学习目标

完成本教程后，你将能够：

- 理解前台 → 后台的范式转变，以及它对「人的角色」的重新定义
- 掌握并行 Agent 集群的三要素：隔离（worktree）、任务粒度、评审带宽预算
- 搭一条 Issue → PR 自动流水线（Slack/Linear/GitHub 触发）
- 判断哪些任务适合后台化，哪些必须留在前台

---

## 一、范式转变：从「盯着干」到「委派 + 验收」

| 维度 | 前台 Agent（W1–W7） | 后台 Agent（W8） |
|------|--------------------|------------------|
| 交互 | 同步对话，人机轮流 | 异步委派，完成通知 |
| 人的注意力 | 过程监督 + 随时纠偏 | 事前写清规格 + 事后验收 |
| 并发 | 1~3 个会话已经手忙脚乱 | 天然并行，云端资源不是瓶颈 |
| 失败成本 | 低（当场看到，随时打断） | 高（跑偏几十分钟才发现） |

范式转变的代价很明确：**你失去了过程监督**。所以后台化的成败完全取决于两个前台时代可以敷衍的环节——

1. **事前**：任务规格必须完整到「陌生人可执行」。Week 2 的 RePPIT 在这里从「可选优化」变成「硬性前提」——后台 Agent 没机会中途问你「这个边界 case 怎么处理」
2. **事后**：验收体系必须机器可判。测试、lint、对照 spec 的审查 pass——它们替你完成 80% 的初筛，人只看剩下的

## 二、并行集群的三要素

### 1. 隔离：worktree 是并行的基础设施

多个 Agent 同时改一个工作目录 = 互相覆盖的灾难。并行的前提是每个 Agent 在自己的 **git worktree**（同一仓库的独立工作副本、独立分支）里干活：

```bash
# 手动版（理解原理用）
git worktree add ../repo-task1 -b feat/task-1
# 产品化形态：各家后台 Agent 产品在云端自动完成 clone + branch + 隔离执行
```

产出统一以分支 + PR 的形式回流，主目录永远干净。冲突在 PR 合并时由既有流程处理——**并行度上去之后，merge 冲突会成为新的排队点，任务拆分时要预留独立性**（尽量让任务动不同的模块）。

### 2. 粒度：什么样的任务适合外包

适合后台化的任务画像：

- **规格可写清**：改动边界明确、验收标准客观（「给 status 端点加缓存，命中率测试覆盖四类状态」）
- **验证可自动化**：有测试兜底，Agent 能自我验证
- **爆炸半径小**：不碰核心架构决策、不动生产凭证

不适合的：探索性任务（「看看怎么重构这块」——需要来回讨论）、跨系统决策（需要组织语境）、弱验证领域（纯 UI 打磨建议留前台走视觉回路）。

### 3. 评审带宽：真正的天花板

「一个人能认真评审几路」就是你的并行度上限。超发的委派只会变成积压的 PR。预算方法：

- 简单任务（依赖升级、小功能）≈ 10 分钟评审 → 可同时 4~6 路
- 中等任务（新模块）≈ 30~60 分钟 → 2~3 路
- 无论多简单，**永远不留「无人在看」的在途 PR**——积压本身就是风险

## 三、Issue → PR 自动流水线

后台 Agent 的规模化形态：让触发器代替人发起委派。

```text
┌──────────────┐   触发    ┌──────────────────┐   领任务   ┌─────────────┐
│ Slack #dev    │ ───────► │ 编排层:           │ ────────► │ 云端 Agent   │
│ Linear 工单   │          │ - 规格补全(模板)   │           │ worktree 隔离│
│ GitHub issue  │          │ - 挑任务/排队     │           │ 实现+自测    │
│ 定时批处理    │          │ - 打标签防重复     │           │ 开 PR        │
└──────────────┘          └──────────────────┘           └──────┬──────┘
       ▲                                                        │
       │              「Fix applied in PR #42, tests green」       ▼
       └──────────────── 通知回源 ◄────────────── 评审门槛: Agent 审查 + 人验收
```

落地要点：

1. **触发即规格化**：工单模板强制字段（背景/期望/验收标准），缺字段的任务进不了队列——把 Week 2 的规格纪律编码进流程
2. **排队与去重**：同一 issue 不重复派发；Agent 领任务先打「in progress」标签
3. **产出必有 PR**：Agent 的一切写入以 PR 到达，没有直推 main 的路径（Week 7 的原则在流水线里的延伸）
4. **失败要有出路**：跑不通的任务自动写评论说明卡在哪、需要什么信息，回到队列或升级给人——**最差的形态是沉默失败**
5. 课程合作方 OpenHands、cmux 等都是这条流水线形态的开源/产品化实现

> 💡 独立开发者的最小版：不需要编排平台。GitHub Actions 定时把「good first issue」类标签的 issue 发给后台 Agent（各家 CLI 的云端模式或 GitHub 的 agent 功能），其余环节天然就是 PR 流程。

## 四、与既有课程的衔接

- 后台集群是 Week 4 **子代理**的组织级放大：子代理在一个会话内分工，后台 Agent 在一台机器/云端分工
- 流水线的评审门槛直接复用 Week 6 的审查架构（多 pass + 分级）；任务规格复用 Week 2 的 RePPIT
- 下一周的 MCP portals 与 LLM gateway 解决的是「几十个后台 Agent 的工具访问与成本」——个人技巧到此升级为组织平台

## 小结

- 后台 Agent 把交互从「过程监督」变为「委派 + 验收」，人的角色上移为规格作者与验收者
- 并行三要素：worktree 隔离（互不踩踏）、任务粒度（规格清、可验证、爆炸半径小）、评审带宽预算（真正的并行度上限）
- Issue→PR 流水线的核心是把纪律编码进编排层：触发即规格化、产出必有 PR、失败要有出路
- 后台化前先问：这事能不能写成「陌生人可执行」的规格？验收能不能机器判？两个都「能」才委派
