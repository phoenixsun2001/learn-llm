# 软件工厂：自运行、自改进的软件系统（CS146S Week 10）

CS146S 的终点站，也是全课理念上最激进的部分。九周铺垫之后，最后一周给出的图景是：**软件不再是一件件被人工建造的产品，而是一个持续自我演进的系统**——需求自动进入、Agent 集群生产、质量门禁自动裁决、线上问题自动诊断并生成新一轮需求。这就是「软件工厂」（Software Factory）。

## 学习目标

完成本教程后，你将能够：

- 说出软件工厂的四个组成部分，以及它与「CI/CD 流水线」的本质区别
- 理解「部署后 Agent」的运行形态与治理要点
- 用 Loop Engineering 的内外循环框架为软件工厂定位
- 对「哪些已经是现实、哪些还在路上」保持校准的判断，并规划自己的最小软件工厂

---

## 一、什么是软件工厂

先排除误解：软件工厂 ≠ 更快的 CI/CD。CI/CD 自动化的是**从代码合并到部署**这一段；软件工厂把自动化的范围扩展到**两端**——上游（需求进入）与下游（线上反馈回流）：

```text
        ┌─────────────────────── 软件工厂 ────────────────────────┐
        │                                                        │
 用户/监控/运营 ──► 需求入口 ──► 生产流水线 ──► 质量门禁 ──► 部署运维
  (意图源)      (intent.md)   (后台 Agent 集群)  (审查+evals)   (灰度/监控)
        ▲                                                        │
        └────────────── 线上发现 → 自动诊断 → 新的 intent.md ◄────┘
```

四个组成部分：

| 组成 | 承接哪一周 | 职责 |
|------|-----------|------|
| **需求入口** | W2 规格 / W8 流水线 | 把人类意图、运营需求、线上异常统一翻译成规格化工件（intent） |
| **生产流水线** | W8 后台 Agent 集群 | 领取意图 → 计划 → 实现，产出永远是 PR |
| **质量门禁** | W6 审查 / W7 安全 | Agent 多 pass 审查 + 测试 + 安全扫描 + 人工裁决点 |
| **部署运维闭环** | 本周新内容 | 灰度发布、监控告警、Agent 值班诊断、异常写回需求入口 |

与 AI 原生 SDLC 的关系：那份 Playbook 是这条流水线的**逐阶段操作手册**；软件工厂强调的是整体的**自运行**——循环由触发器驱动，而不是由人驱动。

## 二、部署后 Agent：运行与治理

软件工厂里最「新」的部分是：**软件部署之后，Agent 仍在工作**。

### 运行形态

1. **值守型**：监控指标越界（错误率、延迟、队列积压）→ 确定性规则触发 → Agent 只读诊断 → 输出诊断报告/开修复 PR
2. **响应型**：用户报告/工单进入 → Agent 复现、定位、给出根因假设与修复建议
3. **巡检型**：定期任务——依赖升级 PR、死代码清理、文档与代码一致性核对

关键设计原则（AI 原生 SDLC 的「控制带」思想）：**检测保持确定性，模型只在被触发后进场**。阈值与规则是普通代码，可测试、可审计；LLM 负责规则之上的诊断与修复——不把「判断是否异常」这件事本身交给概率性组件。

### 治理四条底线

1. **分级自治**：开发环境 Agent 可自由部署；staging 需自动门禁全绿；生产环境的 Agent 只能「准备发布」，发布由人（或强规则）授权
2. **回滚是最熟的路径**：工厂能自动部署，就必须能自动回滚——回滚命令是演练频率最高的一条
3. **审计完备**：每一次自动变更可追溯到「哪个触发器、哪份意图、哪个 Agent、谁批准的门槛」
4. **熔断开关**：一键冻结全部自动变更（「停厂」开关）——任何自动生产线都必须能停下来

## 三、用 Loop Engineering 定位：内外循环

本站的 [Loop Engineering 教程](/tutorials/loop-engineering) 提出过框架，软件工厂恰好是它的完整形态：

- **内循环**（人机结对）：写代码的单次循环——提示 → 生成 → 验证 → 修正。W1–W4 训练的就是这个循环的效率
- **外循环**（组织级演进）：需求 → 实现 → 部署 → 反馈 → 新需求。软件工厂就是把外循环的每一次「换手」都自动化了，人只守循环中的**判断节点**

人在软件工厂里的位置：定义意图与价值观（什么值得做）、设定约束与门槛（红线与质量标准）、裁决机器不确定的事（升级上来的疑难）、为循环本身持续调参（哪些门禁太松/太紧）。**人的工作从「生产软件」上移到「设计生产软件的系统」。**

## 四、现实校准：哪些是真，哪些是愿景

保持清醒的评估：

| 环节 | 现状 |
|------|------|
| 规格 → PR 的自动生产 | ✅ 已可用（W8），规格质量决定一切 |
| Agent 审查 + 安全扫描门禁 | ✅ 已可用（W6/W7），人的裁决点不可省 |
| 值守诊断 + 修复 PR | 🟡 窄场景可用：指标越界归因、依赖升级、明确定义的故障模式 |
| 完全无人干预的自改进 | ❌ 还不行：自动变更的累积效应、目标漂移（optimize for the metric）都需要人守 |
| 从模糊商业意图直达系统演进 | ❌ 远期：意图的澄清本质上是对话性的 |

**人的判断节点不会消失，只会上移、变少、变关键。** 这也是全课反复回归的主题：技术让编码民主化，判断力成为新的稀缺资源。

## 五、实战：设计你的最小软件工厂

不必是斯坦福的课程作业才配做这件事。独立开发者的最小版（本站技术栈即可）：

1. **需求入口**：仓库里建 `intent/` 目录，模板三行——要什么、为什么、怎么算完成（W2 的规格纪律）
2. **生产**：给仓库配 CLAUDE.md + 测试回路（`make test`），把小任务直接委派给后台 Agent（W8）
3. **门禁**：CI 跑测试 + lint + 一条 Agent 审查 pass（W6）；依赖升级类 PR 允许 Agent 自动合并，其余必须人批
4. **闭环**：监控告警（哪怕只是 UptimeRobot + webhook）触发时，用 `claude -p` 非交互跑一次日志诊断，把结论写进 issue（W10 的值守型）
5. **度量**：记录「意图 → 上线」周期时间与每 PR 人工分钟数——这是判断工厂是否真的在省力的唯一标准

先让这条线跑通一个真实的小需求，再逐步扩自动化范围。**工厂是长出来的，不是一次建成的。**

---

## 小结

- 软件工厂 = 需求入口 + Agent 生产流水线 + 质量门禁 + 部署运维闭环；与 CI/CD 的本质区别是把自动化扩展到了上游（需求）与下游（反馈回流）
- 部署后 Agent 有值守/响应/巡检三种形态；铁律是**检测确定性、模型触发后进场**，治理靠分级自治、可回滚、全审计、熔断开关
- 软件工厂是 Loop Engineering 外循环的全自动化形态；人的工作从生产软件上移到设计生产软件的系统
- 现实校准：规格→PR 与机器门禁已可用，值守诊断窄场景可用，完全自改进还需人守判断节点

## 结语：十周学完了什么

十周路线复述一遍：**理解 Agent（W1）→ 武装单个 Agent（W2–W4）→ 改造环境（W5–W7）→ 规模化组织化（W8–W10）**。课程教的不是「怎么用某个工具」，而是一套正在成型的软件工程新范式：人定义意图，Agent 执行，人与 Agent 共同评估和迭代。工具会过时，范式与判断力不会。
