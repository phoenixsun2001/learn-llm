## 核心方法论：四阶段工作流

面对一个有真实复杂度的任务（比如「给一个陌生模块加新功能」「排查一个隐蔽 bug」），最高效的做法是遵循**探索 → 规划 → 执行 → 校验**四阶段。每个阶段调用 ZCode 最合适的能力：

```
┌─────────────────────────────────────────────────────────┐
│                  四阶段工作流                             │
│                                                          │
│  ① 探索（Explore 子智能体）                              │
│     委派只读调研：摸清现状、调用链、数据结构、测试覆盖     │
│     产出：精炼的结论（而非原始代码片段堆砌）              │
│          ↓                                                │
│  ② 规划（主 Agent）                                      │
│     基于探索结论设计方案：要改哪些文件、风险在哪、分几步   │
│     产出：清晰的实现方案，由你确认方向                    │
│          ↓                                                │
│  ③ 执行（主 Agent + 目标模式）                           │
│     用 /goal 设定可校验目标，让 Agent 自主迭代实现        │
│     产出：完成的代码改动                                  │
│          ↓                                                │
│  ④ 校验（目标模式自动 + 人工复核）                        │
│     测试通过、类型检查通过、diff 复核                     │
│     产出：可交付的结果                                    │
└─────────────────────────────────────────────────────────┘
```

这套方法论的核心思想是**能力分工**：让只读的子智能体负责摸清情况，让目标模式负责把执行推进到底，而你和主 Agent 负责关键的决策与方向把控。

## 实战演练：为一个模块添加监控埋点

用一个典型需求把四阶段跑通：**为现有的支付模块添加请求监控埋点**。这是个中等复杂度任务——既需要先搞清楚现有代码结构，又需要跨多个文件实现，非常适合演示完整工作流。

### 阶段一：探索

任务一开始，你对支付模块可能并不完全了解。先不要让主 Agent 急着动手，而是**委派 Explore 子智能体**去调研：

```text
先帮我搞清楚 src/payment/ 这个模块：
1. 所有对外暴露的入口函数，以及它们的调用关系
2. 现有的日志机制（用什么 logger，记了什么）
3. 是否已有任何埋点或监控相关的代码
4. 项目里其他模块是怎么做监控的（如果有的话），给我一个参考

调研清楚后，把结论汇总给我，先不要改代码。
```

关键点：
- **明确要求「先不要改代码」**——探索阶段只读，避免误改
- **要求汇总结论**——而不是把所有相关代码贴给你，节省主 Agent 的上下文

Explore 会返回一份精炼的调研报告：入口在哪、现有日志怎么打的、有没有可复用的埋点工具。这份结论是后续所有决策的基础。

### 阶段二：规划

拿到探索结论后，让主 Agent 基于它**设计方案**，但同样先不实现：

```text
基于上面的调研，给我一个添加请求监控埋点的方案：
- 要在哪些位置埋点（列出具体函数/文件）
- 每个埋点要记录哪些字段（方法名、耗时、状态、错误信息等）
- 如何复用现有的 logger / 是否需要新建埋点工具
- 实现风险点在哪

先给我方案，我确认后你再动手。
```

为什么规划阶段也要单独做？因为**方向错了，执行再快也是白费**。花一分钟确认方案，能省掉后面几十分钟的返工。看到方案后，你可以提出调整（比如「错误埋点的级别用 warn 而非 error」），确认无误再进入执行。

### 阶段三：执行

方案确认后，用**目标模式**让 Agent 自主实现：

```text
/goal 按照确认的方案，为 src/payment/ 的所有入口函数添加监控埋点，
要求：
- 记录方法名、入参摘要、耗时、状态（success/fail）、错误信息
- 复用现有的 logger，不引入新依赖
- 补充埋点相关的单元测试
- 确保 npm run test 和 npm run build 全部通过
```

设定目标后，Agent 会自主迭代：逐个函数加埋点 → 跑测试 → 修报错 → 再跑，直到目标达成。你不需要盯着看，完成时它会通知你。

### 阶段四：校验

目标模式报告完成后，做最终复核：

1. **看 diff**：在文件树查看 Git 改动，确认埋点位置和方案一致
2. **看测试**：新增的测试是否真的覆盖了埋点逻辑（而不是空壳测试）
3. **看边界**：失败路径的埋点是否正确触发、耗时统计是否准确

如果发现问题，继续用目标模式或对话迭代。满意后接受改动，任务完成。

## 何时该用什么能力：决策清单

掌握工作流后，关键是灵活应变。下面是常见场景的能力选择：

| 场景 | 推荐能力 | 理由 |
|------|---------|------|
| 陌生代码、要改但不知道在哪 | 先 Explore 再主 Agent | 先摸清再动手，避免盲改 |
| 意图明确的机械改动 | 直接对话或低推理强度 | 不必过度规划，快速执行 |
| 多步骤、有明确验收标准 | 目标模式 | 让 Agent 自动迭代到完成 |
| 模糊需求、需要权衡 | 高推理强度 + 规划阶段 | 充分思考再行动 |
| 大范围检索/调研 | Explore 子智能体 | 只读、归纳、不污染主上下文 |

记住一个总原则：**读多写少时委派子智能体，写多读少时用主 Agent，需要持续推进时上目标模式**。

## 避免常见误区

熟练运用工作流后，也要警惕几个反模式：

- **跳过探索直接动手**：面对不熟悉的代码直接让 Agent 改，十有八九会跑偏。探索的投入永远值得。
- **目标定得太大太模糊**：把「重构整个系统」塞进一个 `/goal`，Agent 容易迷失。拆成聚焦的小目标更有效。
- **只看结果不看过程**：直接接受 Agent 的产出而不复核 diff，隐患会累积。校验是质量的最后防线。
- **过度委派**：连一个 3 行的小修改也要走完整四阶段，纯属浪费时间。简单任务直接对话即可。

工作流是工具，不是教条。根据任务复杂度灵活裁剪，才是真正的高手。
