# Trae SOLO Builder 实战指南

Trae 是面向真实项目开发的 AI IDE。它不只是把 AI 放进侧边栏，而是让 AI 读取项目上下文、拆解任务、生成 PRD、编写代码、打开预览，并在你确认后继续迭代。

SOLO Builder 适合“从想法到可运行 Web 应用”的场景：你给出自然语言需求，它负责整理需求、生成实现方案、写代码并产出可预览结果。这个教程会带你完成一次完整的小项目练习。

## 你将学会什么

- 判断什么时候用 Trae IDE，什么时候切到 SOLO Builder
- 写出能让 Builder 正确理解项目目标的需求说明
- 审查 PRD、TODO、代码变更和预览结果
- 用小步反馈推动 AI 继续迭代
- 在交付前检查代码质量和产品体验

## 第 1 步：认识 Trae、SOLO 与 Builder

Trae 常见有三类使用方式：

| 模式 | 适合场景 | 你需要关注什么 |
| --- | --- | --- |
| 普通 IDE / Chat | 解释代码、局部修改、补全函数 | 给清楚文件范围和修改目标 |
| SOLO Builder | 从需求快速生成应用或页面 | 需求、验收标准、预览效果 |
| SOLO Coder | 复杂项目开发、重构、修 bug | 任务拆解、代码审查、测试结果 |

SOLO Builder 的优势是端到端：它会把需求变成文档、计划、代码和预览。缺点是如果需求太模糊，它也可能生成看起来完整但不符合业务的页面。

因此你的角色不是“等 AI 交付”，而是“提供上下文、审查方案、控制范围”。

### 练习目标

本教程建议你用 Trae 做一个小型 Web 应用：

```text
一个 AI 工具学习卡片页面，展示工具名称、适合人群、学习步骤、官方链接和下一步行动。
```

这个练习足够小，适合第一次熟悉 Builder；同时又包含真实页面常见的信息结构和响应式要求。

## 第 2 步：准备项目上下文

在开始生成前，先准备一份需求说明。不要只写“帮我做一个页面”，而是提供项目边界。

### 推荐输入模板

```text
我要做一个中文 AI 学习网站里的工具学习卡片页面。

目标用户：
- 正在学习 AI 编程和 AI 工作流工具的人
- 希望按步骤掌握一个具体工具

页面需要展示：
- 工具名称
- 工具分类
- 一段简洁介绍
- 适合人群
- 5 个学习步骤
- 官方链接
- 下一步行动按钮

技术约束：
- React + Vite
- 不使用 TypeScript
- 样式使用现有 CSS custom properties，例如 var(--text-primary)
- 保持中文 UX 文案
- 不要引入新依赖

请先输出实现方案，不要立刻写代码。
```

### 如果你在现有项目中开发

还要补充这些内容：

- 参考哪个已有页面
- 路由文件在哪里
- 数据文件在哪里
- 组件命名规则是什么
- CSS class 命名规则是什么

示例：

```text
请参考 src/pages/Tools/ToolDetail.jsx 和 ToolDetail.css。
新增内容要保持现有卡片、徽章、时间信息和中文文案风格。
只修改工具详情相关文件。
```

## 第 3 步：让 Builder 先生成 PRD 和计划

进入 SOLO 模式后，选择 SOLO Builder。第一轮不要急着让它写代码，先让它生成 PRD 和 TODO。

推荐提示词：

```text
请基于上面的需求生成一份简短 PRD，包括：
1. 页面目标
2. 信息架构
3. 主要状态
4. 验收标准
5. 你计划修改的文件

先不要写代码。
```

你要重点检查：

- 页面目标是不是准确
- 是否误解了用户群体
- 是否加入了不需要的营销区块
- 是否准备修改无关文件
- 验收标准是否能被检查

如果 PRD 不对，先改 PRD，不要进入编码。

### 好的反馈方式

```text
这个方案的方向对，但页面不需要营销式 hero。
请改成工具型详情页结构：顶部介绍、学习步骤、适合人群、官方链接。
不要新增全局布局。
```

## 第 4 步：生成代码并审查 Diff

确认计划后，再让 Builder 实现。

推荐提示词：

```text
按确认后的 PRD 实现。
要求：
- 保持现有中文 UX 语言
- 不新增依赖
- 使用现有设计 token
- 移动端不能出现文本溢出
- 完成后说明修改了哪些文件
```

实现后打开 DiffView 或代码差异，按下面清单审查。

### 代码审查清单

| 检查项 | 通过标准 |
| --- | --- |
| 文件范围 | 只修改需求相关文件 |
| 数据结构 | 字段命名清楚，不制造重复数据 |
| 文案 | 中文、简洁、和站点语气一致 |
| 样式 | 使用 CSS token，不硬编码大段颜色 |
| 响应式 | 小屏下按钮、标题、卡片不挤压 |
| 可维护性 | 没有把业务逻辑塞进长字符串 |

如果发现问题，用具体反馈推动修正：

```text
当前卡片底部在移动端会换行拥挤。
请调整 footer 为可换行布局，并让箭头保持在右侧。
只改 CSS。
```

## 第 5 步：运行预览并做交互验收

Trae 生成页面后，需要跑一次本地预览。你可以让它执行项目已有命令，也可以自己运行：

```bash
npm run dev
```

如果是生产构建检查：

```bash
npm run build
```

预览时按下面顺序看：

1. 页面能否正常打开
2. 数据是否都显示出来
3. 学习步骤是否能点击
4. 官方链接是否打开新窗口
5. 移动端是否有遮挡、溢出或过密
6. 空状态是否仍然可读

不要只看桌面端。很多 AI 生成页面的问题都出现在小屏布局。

## 第 6 步：用反馈继续迭代

Builder 适合小步迭代。每轮只给一个明确任务。

### 文案迭代

```text
请把学习步骤的标题改得更像操作向导，不要像功能介绍。
每个标题控制在 8 个字以内。
```

### 结构迭代

```text
请在学习步骤前增加“适合人群”和“完成后你将能够”两个区块。
保持当前视觉风格，不要新增卡片嵌套卡片。
```

### 质量修复

```text
请检查这个页面是否有硬编码颜色、负 letter-spacing、过大的圆角。
只修样式问题，不改数据内容。
```

## 第 7 步：交付前检查

完成前，让 Trae 做一次自查：

```text
请基于本次改动做交付检查：
1. 修改了哪些文件
2. 是否符合原始需求
3. 是否有未验证的风险
4. 建议我运行哪些命令确认
```

你自己再确认：

- 是否有无关文件被改动
- 是否生成了多余缓存或日志
- 是否能构建
- 是否能回到原有交互路径

## 常见问题

### Builder 生成的内容太泛

通常是需求没有写清楚目标用户、信息结构和验收标准。先补需求，不要直接要求“重新做”。

### Builder 修改了太多文件

让它先列计划，并明确“只修改这些文件”。如果已经改乱了，先查看 diff，再决定保留哪些改动。

### 页面看起来像营销页

工具型页面应该重视扫描、比较和下一步行动。减少大段愿景文案，突出步骤、状态和链接。

### 生成代码可运行但不好维护

要求它拆分数据和展示逻辑，复用现有组件模式，并删除没有使用的字段。

## 推荐提示词合集

### 开始前

```text
请先阅读项目结构，理解现有页面风格，然后输出实现方案，不要写代码。
```

### 实现时

```text
按方案实现，保持现有中文 UX 和设计 token，不新增依赖。
```

### 修问题

```text
请只修复这个问题：<具体问题>。不要改动无关文件。
```

### 收尾

```text
请总结本次改动、验证方式和剩余风险。
```

## 小结

Trae SOLO Builder 的正确用法不是“让 AI 一次性做完整项目”，而是：

```text
清楚需求 → 确认 PRD → 小步实现 → 审查 Diff → 预览验证 → 继续迭代
```

你越能提供清晰上下文，Builder 越像一个可靠的项目协作者。
