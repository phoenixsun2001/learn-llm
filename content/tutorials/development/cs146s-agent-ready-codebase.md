# Agent-Ready 代码库：让仓库对 AI 友好（CS146S Week 5）

CS146S 进入第三层「改造环境以适配 Agent」（Week 5–7）。这一层的洞察是：**当 Agent 产出代码的速度大幅提升，瓶颈会转移到验证、审查和安全**——而代码库本身，必须先重构为「可被 Agent 理解和检验」的形态。

本周回答一个具体问题：什么样的仓库能让 Agent 一次做对？答案是四个支柱——结构、文档、测试、检查。它们恰好也是传统软件工程的好品味，只是现在多了一层新含义：**读者不再只有人类，还有 Agent**。

## 学习目标

完成本教程后，你将能够：

- 从 Agent 的视角审视一个仓库：它能「看见」什么、「验证」什么
- 掌握 Agent-Ready 仓库的四支柱改造要点
- 用一份可量化的「就绪度」检查表给自己的仓库打分
- 为遗留仓库规划一条渐进改造路径

---

## 一、换位思考：Agent 眼中的你的仓库

一个新会话的 Agent 面对你的仓库时，它**没有**：项目历史、团队口口相传的约定、「这个目录别动」的默契。它只有：上下文窗口里的东西 + 工具能读到的东西。

于是它在你的仓库里的体验是这样的：

| Agent 的处境 | 仓库的问题 | 后果 |
|-------------|-----------|------|
| 不知道从哪读起 | 巨型单体文件、无层级目录 | 盲目 grep，读错重点 |
| 不知道规矩是什么 | 没有 CLAUDE.md/AGENTS.md | 按通用惯例行事，风格与项目冲突 |
| 不敢动手改 | 没有测试 | 改一处不知会不会破坏另一处 |
| 改完不知道对不对 | 构建慢、命令散落各处 | 只能「看起来对」就交差 |

反过来，一个 Agent-Ready 的仓库让每个新会话都站在前人肩膀上：**五分钟读懂结构，一分钟知道规矩，一行命令验证改动**。

## 二、四支柱改造

### 支柱 1：结构——可导航性优先

- **模块化、单一职责**：Agent 的上下文窗口有限，「读一个目录就懂一个子系统」的结构远比「一个 3000 行的 utils.ts」友好
- **惯例即文档**：目录名用行业通用语义（`routes/`、`components/`、`processors/`、`tests/`），Agent 的先验知识直接生效
- **入口与边界清晰**：README 第一屏给出架构鸟瞰图（谁调用谁、数据流向）；生成代码、冻结代码放独立目录（`src/gen/`）并配 Hooks 保护
- **一个信号**：如果人类新人需要你口头讲解才能定位某个功能，Agent 也一样需要——先修结构

### 支柱 2：文档——写给「第一天的新人」

- **CLAUDE.md / AGENTS.md**：命令、约定、已知坑（Week 4 已详述）——这是 Agent 的第一读物
- **README 按任务组织**：不只「这是什么项目」，更有「怎么跑起来、怎么加一个功能、怎么发一个版」
- **ADR（架构决策记录）**：`docs/adr/0007-why-clickhouse.md` 这样的文件，把「为什么当年这么选」写成文字——否则 Agent 会自信地「简化」掉它不理解的复杂度
- **文档策略**：宁可少而准，不要多而腐。文档也是上下文，过期的文档是负资产

### 支柱 3：测试——Agent 的安全网与回路的燃料

- **快速、可单跑、确定性**：`make test` 一条命令、几十秒内出结果、不 flaky。慢而 flaky 的测试套件会让 Agent 的自我验证回路瘫痪——它要么等不起，要么被随机失败带偏
- **测试是规格的可执行形式**：Agent 改代码前先读测试，就能读懂「这里的行为契约」；先写失败测试再修（TDD 红绿循环），是约束 Agent 最有效的缰绳
- **按层组织**：单测快而多，集成测试覆盖关键路径，端到端少量冒烟——让 Agent 能选「改这一行只需要跑哪一层」

### 支柱 4：检查——让机器守住底线

- **本地与 CI 同一套检查**：lint、类型检查、格式化。Agent 在本地就能跑的检查，才会在提交前自我纠正
- **检查要进 Hooks 与 CLAUDE.md**：PostToolUse 自动修复风格问题；「构建即验证」写进项目记忆
- **CI 是最终裁判**：PR 上的绿灯是 Agent 产出的验收标准，也是下一周「Agentic 代码审查」的输入

## 三、量化：仓库就绪度检查表

课程强调「如何量化评估就绪度」。下面这份检查表可用于自评（每项 0/1/2 分）：

| 维度 | 检查项 | 分值 |
|------|--------|------|
| **可发现性** | README 有架构鸟瞰与新手上路路径 | 0/1/2 |
| | 目录结构符合行业惯例，无 3000 行级巨型文件 | 0/1/2 |
| | 有 CLAUDE.md/AGENTS.md 且含准确的命令清单 | 0/1/2 |
| **可理解性** | 关键决策有 ADR 或等价的「为什么」文档 | 0/1/2 |
| | 生成代码/冻结区有明确标注与保护 | 0/1/2 |
| **可验证性** | `make test`（或等价）一条命令全绿，< 2 分钟 | 0/1/2 |
| | 测试无 flaky，失败可复现 | 0/1/2 |
| **可守护性** | lint/类型检查本地可跑且已接入 CI | 0/1/2 |
| | 关键路径有 Hooks/CI 门禁（禁推 main、保护目录） | 0/1/2 |

- **14–18 分**：Agent-Ready，可以放心让 Agent 大规模参与
- **8–13 分**：可用，但 Agent 产出需要更多人工复核，优先补「可验证性」
- **0–7 分**：先修仓库再上 Agent——否则省下的编码时间会变成加倍的验证时间

> 💡 注意权重：四支柱里**测试的杠杆率最高**。一个快而可靠的测试套件能把 Agent 从「危险的批量生成器」变成「带安全网的自动化同事」。如果只能先做一件事，就做这个。

## 四、遗留仓库的渐进改造

不必推倒重来。按回报排序的路径：

1. **第一天**：写 CLAUDE.md（哪怕只有命令清单）+ 接入 lint + 修 flaky 测试
2. **第一周**：给最常改动的子系统补测试；把「为什么」写成 3~5 篇 ADR
3. **第一个月**：拆最大的三个巨型文件；统一检查工具进 CI 与 Hooks
4. **持续**：每次人肉排雷（「哦这个目录不能动」）都沉淀为文字——和 Week 4 的「错误两次法则」同一精神

## 小结

- Agent 只有上下文与工具，没有项目默契——仓库必须把「默契」显式化成结构与文字
- 四支柱：结构（可导航）、文档（写给第一天的新人）、测试（Agent 的安全网）、检查（机器守底线）
- 就绪度可以量化：可发现性、可理解性、可验证性、可守护性四维打分，测试杠杆率最高
- 改造是渐进的：先让 Agent 能验证（测试+lint），再让它能理解（文档+ADR），最后让它守规矩（Hooks+CI）
