单机能跑、CI 能发之后，新问题在规模处等你：测试数据和用户数据混在一个库、一次发版全体用户同时看到半成品、负载上来一台机器扛不住。"部署架构"就是把**环境、流量、数据、配置**四件事规划清楚，让系统随业务长大而不用推倒重来。

本篇是全链路路径的架构篇——不谈具体工具，谈结构决策。

## 你将学到

- 环境划分（dev/staging/prod）与各环境纪律
- 从单机到多实例的演进路径与反向代理层
- 数据层设计：卷、备份、迁移的规矩
- 配置分层与密钥管理策略
- AI 应用特有的架构考量（GPU、长任务、模型版本）

## 环境划分：三个世界，三种纪律

| 环境 | 目的 | 数据 | 谁能改 |
|------|------|------|--------|
| **dev** | 日常开发调试 | 造的数据，随便造 | 开发者 |
| **staging（预发）** | 上线前彩排，尽量像生产 | 脱敏后的生产形态数据 | CI 自动部署 |
| **prod（生产）** | 真实用户 | 真数据，受保护 | 仅 CD / 受控流程 |

三条纪律：

1. **生产环境没有"手动试一下"**——一切改动走发布流程，哪怕是改一行配置。
2. **staging 与 prod 同构**（同版本依赖、同 compose 结构、同 Nginx 入口），只差规模与密钥——否则彩排没有意义。
3. **数据永不跨级复制覆盖**：可以 prod → 脱敏 → staging，永远不能 staging → prod。

小团队务实版：dev（本机/容器）+ prod 起步，staging 在用户变多、发版变频繁后再补。

## 流量层：单机 → 多实例的演进

**阶段一：单机单实例**（本平台现状即此）

```text
用户 → Nginx(80/443) → frontend容器(8001) / backend容器(8400)
```

够用、简单、可观测。**不要过早进入下一阶段。**

**阶段二：单机多实例**——单个服务扛不住时，先横向复制它自己：

```text
用户 → Nginx
        ├─ /api/ → upstream api_pool { 127.0.0.1:8401 127.0.0.1:8402 }
        └─ /    → frontend
```

前提：实例**无状态**（会话在 Redis/JWT，文件在对象存储/共享卷）——无状态是多实例的门票。

**阶段三：多机**——流量或可用性要求跨机器：加一层负载（云 LB 或 Nginx 主机），机器间用 Docker Swarm/K8s 管编排。走到这步通常意味着你已经有专职运维视角了。

**健康检查是每一阶段的标配**：compose 里 `healthcheck:` 定义探活，Nginx 用 `max_fails` 剔除坏实例——坏实例自动摘除，是"稳定"的最低保障。

## 数据层：卷、备份、迁移

数据是架构里唯一"错了会痛一辈子"的部分，三条规矩：

1. **有状态的一律进卷/托管服务**：数据库、上传文件、生成素材（本平台把 `content/`、`pipeline/data/` 全走 bind mount，容器可随意重建）。
2. **备份是流程不是愿望**：数据库每日 dump 进对象存储/异地；备份要**演练恢复**——没恢复过的备份等于没有。SQLite 一个 `sqlite3 .backup` 脚本 + cron 就是起步。
3. **迁移（migration）走版本化**：数据库结构变更写成带版本的迁移脚本（Alembic/Flyway 等），随代码走 CI——杜绝"上线时手动 ALTER TABLE"。

## 配置分层

推荐四层配置，从"变得最慢"到"变得最快"：

```text
代码默认值（仓库）
  → 镜像构建参数（如 VITE_ 前端变量）
    → 环境变量 / .env（每个环境一份）
      → 运行时配置（启动参数、环境内开关）
```

密钥单独一条线：**只走环境变量或密钥管理服务**，日志、镜像层、代码库三处绝不允许出现。

## AI 应用的架构特项

通用架构之外，AI 应用有三个特殊考量：

- **GPU 是稀缺资源**：推理服务独立成层（独立容器/独立机器），按队列削峰；CPU 服务与 GPU 服务分开伸缩——Web 层扩 10 倍不代表 GPU 也要扩。
- **长任务与流式**：生图/生视频这类几十秒到几分钟的任务不能阻塞 Web 请求线——任务队列（Redis/Celery/RQ）+ 状态轮询/SSE 推送，是 AI 产品的标准形态。
- **模型版本即架构**：换模型=换行为，把"模型名/模型版本"做成配置项并记录在每次请求日志里，出问题才能归因（本平台 `ZHIPU_MODEL` 环境变量即是此用途）。

## 典型场景

- **场景 A：AI 问答站从 0 到 1000 用户。** 单机三容器（前端/API/DB）起步；负载高时先把 API 扩双实例 + Redis 会话；GPU 推理放队列后按需加卡——每一步都有明确的触发条件，不预支复杂度。
- **场景 B：内容平台要灰度。** Nginx 按 cookie/比例分流（`split_clients`），5% 流量进新版本容器，观察后放量——下一篇详细展开。
- **场景 C：本平台的部署复盘。** 双容器 + 三卷 + Nginx 入口 + 环境变量配置——阶段一的标准形态；若素材管道要跑 ML 推理，就拆出 GPU worker 容器 + 队列。

## 小结

部署架构的本质是**给未来留好接缝**：环境分级让发版有彩排，无状态让扩容成为可能，卷与备份让数据活过一切事故，分层配置让变更可控。不需要一步到位，但需要在每一步走对方向。
