# AI 原生团队：MCP Portals、LLM Gateway 与成本治理（CS146S Week 9）

CS146S 第四层第二周。前九周的技巧都属于个人或小队；本周视角切到**组织**：当几十上百个工程师、几百个后台 Agent 同时在用 LLM 时，会发生什么？

答案是：工具访问失控（每人自己配一套 MCP，权限与审计无从谈起）、成本失控（没人知道这个月 token 花在哪）、质量参差（有人用好模型做杂活，有人用弱模型做核心业务）。本周的解法是把个人技巧**平台化**：MCP portals、LLM gateway、模型路由，以及组织级推广模式。

## 学习目标

完成本教程后，你将能够：

- 理解 AI 原生团队与「给每人发个 API key」的差别：集中、带权限、可观测
- 设计 MCP portal：组织级工具目录 + 统一授权
- 理解 LLM gateway 的四大职责与模型路由的分级策略
- 用数据（而非感觉）推动组织级推广

---

## 一、为什么个人技巧到组织会失效

Week 2–7 的技巧（上下文工程、Skills、Hooks、审查）假设：一个有判断力的人，管着自己的一个 Agent。组织的现实是：

- **异构性**：工程师用 Claude Code、Codex、ZCode、各家 IDE 插件；同一份内部数据要接 N 次
- **不可见性**：谁在用什么工具、访问什么数据、花了多少钱——没人说得清
- **风险集中化**：一个工程师把内部 API 接进某个第三方 MCP server，泄露面就是全公司的数据

结论：组织需要在个人与模型/工具之间插一层**平台**。这和微服务时代的「API 网关 + 服务目录」是同构问题，连答案都相似。

## 二、MCP Portal：组织级工具目录

Week 2 学过 MCP 三角色（Host/Client/Server）。MCP portal 是在生态之上的**治理层**：

```text
工程师的 Agent (Host)
        │  只连一个入口
        ▼
┌─ MCP Portal ──────────────────────────────┐
│  工具目录: 官方 Server + 内部自建 Server     │
│  权限中枢: 谁能用哪个工具、什么范围、多久过期  │
│  审计日志: 谁、何时、调了什么、动了哪些数据    │
│  网关能力: 限流 / 脱敏 / 密钥托管            │
└───────────────────────────────────────────┘
        │
   ▼ GitHub MCP   ▼ 数据库 MCP   ▼ 内部平台 MCP ...
```

核心收益：

1. **一次建设**：内部系统的 MCP Server 由平台组写一次，全员可用——不再是每个团队各写一遍集成脚本
2. **权限即配置**：「实习生 Agent 可以读代码库，不能碰生产数据库」变成 portal 里的一条配置，而不是口头约定
3. **审计闭环**：Week 7 的「假设 Agent 会被攻破」在组织级的落地就是**可审计的工具访问**——事后能回答「那个 Agent 当时能碰到什么」

## 三、LLM Gateway：统一接入层

Gateway 是所有 LLM 流量的唯一入口，四个职责：

| 职责 | 内容 | 对应的组织痛点 |
|------|------|---------------|
| **统一接入** | 一套 API 兼容多家模型供应商；换供应商不改业务代码 | 供应商锁定；Key 散落在各处 |
| **可观测** | 每次调用记录：谁、哪个应用、什么任务、多少 token、延迟、质量信号 | 「这个月 AI 账单为什么翻倍」无人能答 |
| **成本归因** | 按团队/项目/功能维度分摊成本，做预算与告警 | 成本是共享池，无人爱惜 |
| **治理** | 内容审计、敏感数据过滤（防 PII 进外部模型）、按合规要求路由 | 数据出境合规 |

课程合作方里的 Phoenix（Arize）代表的就是可观测这条线：Agent 的调用链追踪与质量评估，是 Gateway 生态的标准组件。

## 四、模型路由与成本优化

### 路由：不是「选一个最好的模型」，而是「给每类任务配刚好够用的模型」

```text
任务分级                    模型档位          成本量级
─────────────────────────────────────────────────
架构设计/疑难调试           旗舰模型          $$$$
日常功能实现/后台 Agent 任务  中档模型          $$
代码补全/分类/摘要/格式转换   小模型            ¢
批量离线任务                小模型 + 异步      ¢ (走低价时段/批量接口)
```

三条路由原则：

1. **按任务而非按人头配模型**：同一个人上午做架构、下午跑批处理，不该用同一个模型
2. **升级要有据**：默认中档，检测到任务难度信号（重试次数、评审打回率）再升级旗舰——而不是全局无脑旗舰
3. **缓存优先于推理**：相同的系统提示词、重复的文档块走 prompt cache；内部知识库问答先过 RAG 检索再决定要不要大模型

### 成本治理的度量

- **单位产出成本**：不是「这个月花了多少钱」，而是「每合并 1 个 PR 花多少 / 每解决 1 个工单花多少」——只有这个口径能回答「AI 到底省没省钱」
- **浪费审计**：Gateway 日志里找「小模型就能干的活用了旗舰」与「失败重试风暴」，通常是最大的两块浪费

> 💡 本站 [如何选择适合的大模型](/tutorials/choose-llm-model) 讲的是个人选型决策；本周把它升级为组织级：选型不再是每个人的每周决策，而是路由表里的一行配置。

## 五、组织级推广：从试点到默认

工具再好，「只有极客在用」就没有组织收益。可复制的推广模式：

1. **试点先行**：选 1~2 个有度量基线的团队跑 6 周，攒下「周期时间、评审打回率、单位产出成本」的对照数据
2. **卓越中心（CoE）小而精**：2~3 人维护 portal/gateway/最佳实践 Skills，服务全员而不是管控全员
3. **冠军机制**：每个团队一名「AI 冠军」，负责本团队的上下文资产（CLAUDE.md、Skills）与新人辅导
4. **默认开启，退出自由**：新项目默认带 Agent 基础设施（模板仓库内置 CLAUDE.md + Hooks + CI 审查），反对者可以不用，但不再需要自己搭
5. **指标看板公开**：采纳率、周活使用者、单位产出成本、回滚率——让数据引发团队间良性比较

## 小结

- 组织与个人的分野：异构、不可见、风险集中——解法是把技巧平台化
- MCP portal = 工具目录 + 权限中枢 + 审计日志，让「Agent 能用什么工具」成为可配置、可审计的治理对象
- LLM gateway 四职责：统一接入、可观测、成本归因、数据治理
- 模型路由按任务分级配模型（旗舰/中档/小模型），缓存优先于推理；成本用「单位产出成本」度量
- 推广靠试点数据、小 CoE、冠军机制、默认开启——目标是让正确的事成为默认的事
