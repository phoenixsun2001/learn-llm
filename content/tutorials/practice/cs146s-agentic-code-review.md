# Agentic 代码审查：能力边界与落地架构（CS146S Week 6）

CS146S 第三层第二周。当 Agent 写代码的速度上来之后，**审查成为新的瓶颈**：人肉逐行评审既跟不上产量，也未必比机器更稳。本周讲清三件事：AI 审查擅长什么、遗漏什么，以及怎么设计一套可嵌入团队 PR 流程的审查架构。

## 学习目标

完成本教程后，你将能够：

- 准确说出 AI 审查的能力边界：哪些 pass 它比人强，哪些判断必须留给人
- 用「多 pass + 分级 + 降噪」设计审查架构，而不是丢一句「帮我看看这个 PR」
- 把评审政策写成 REVIEW.md——审查标准即代码
- 将 Agent 审查接入 GitHub PR 流程，同时保住职责分离

---

## 一、AI 审查擅长什么、遗漏什么

### 擅长的（边际成本趋近于零的全面性）

| 能力 | 为什么 AI 强 |
|------|-------------|
| 全量 pass 不知疲倦 | 每个都查：边界条件、空值、并发、资源泄漏——人评审第 40 个 PR 时做不到 |
| 跨文件一致性 | diff 里改了函数签名，Agent 能找出全部调用点是否同步 |
| 对照规格核对 | 拿 spec.md/plan.md 逐条对照实现，「做没做要求的事」机器最擅长 |
| 安全模式扫描 | 注入、硬编码密钥、不安全的反序列化——模式识别是模型强项 |
| 风格与惯例执行 | 项目约定（命名、错误处理模式）机械核对，且不怕得罪人 |

### 遗漏的（必须留给人）

1. **业务意图**：代码正确地实现了错误的需求。Agent 没有用户的痛苦、市场的语境
2. **隐性架构权衡**：「这里用缓存还是直查」背后是团队对未来演进的判断
3. **组织语境**：这段 hack 是已知债务还是无人知晓的雷？git blame 告诉不了它开会决定的事
4. **风险嗅觉的「元判断」**：这个改动**值得**多深的审查？涉及支付核心和改文案显然不同

结论不是「AI 审查不可靠」，而是**分工**：机器做穷举与一致性，人做意图与权衡。人的评审上移一层——从逐行读 diff，变成判断 Agent 标记出来的东西。

## 二、审查架构：多 pass、分级、降噪

丢给 Agent 一句「review this PR」得到的是一团不分轻重的评语。工程化的审查架构有三个组件：

### 1. 多 pass：每个 pass 一个明确视角

```markdown
## Passes（每个发现标注所属 pass）
- **Bugs**: 逻辑错误、边界破损、隐蔽回归
- **Security**: 注入风险、认证缺口、日志中的 PII、硬编码密钥
- **Compliance**: 与 spec.md/plan.md 的一致性、违反项目红线
```

多 pass 的本质是**单次注意力聚焦**：一次只让模型带着一个视角读 diff，比一次带着十个视角读更准。

### 2. 分级：Important 与 Nit 分开

```markdown
## Important 的定义
只把会破坏行为、泄露数据或违反政策的发现标为 Important。
风格与命名是 Nit。每次评审 Nit 最多报 5 条，其余汇总为计数。
```

没有分级的审查报告会被整个忽略——这是 most AI review 无人采纳的第一原因。

### 3. 降噪：明确「不要报告」清单

生成文件、CI 已强制执行的内容（lint 已查的东西）、纯重命名、锁文件——全部写进排除项。信噪比是审查工具的生命线。

## 三、评审政策即代码：REVIEW.md

把上面所有决策放进仓库根目录的 `REVIEW.md`，由技术负责人维护、走代码评审变更。它就是 Agent 审查时的「审查提示词内核」：

```markdown
# 本仓库评审政策

## 范围
所有 PR 都跑三个 pass（Bugs/Security/Compliance），配置见 .github/workflows/review.yml

## 分级与上限
Important：破坏行为/泄露数据/违反政策。Nit：其余。Nit 上限 5 条/次。

## 不报告
src/data/（脚本生成）、CI 已覆盖项、package-lock.json

## 人的评审重点
意图与风险：PR 描述是否说清动机；安全相关改动必须人工确认；数据库 schema 变更需 DBA 复核
```

政策变更 = 改文件 + 评审 + 合并，全员与全部 Agent 下一个 PR 自动生效。**审查标准从「资深工程师的习惯」变成版本化的仓库资产。**

## 四、嵌入团队 PR 流程

### 接入形态

1. **最快起步**：托管审查服务（GitHub App 一键装）
2. **要控制流水线**：自家 CI 里跑审查 action（如 claude-code-action / 各家 CLI 的非交互模式），策略自己掌控

### 典型工作流

```text
PR 提交 ──► CI: 测试 + lint ──► Agent 多 pass 审查 ──► 按 pass 分级的报告挂在 PR
                                        │
   评审意见 @bot 「fix #2」 ──► Agent 修改并推送 ◄──┘
                                        │
                                        ▼
                     人只看：Important 项 + 意图 + 风险 ──► approve / 打回
```

### 必须守住的职责分离

- **写代码的 Agent 无权批准自己的代码**：审查 Agent 与实现 Agent 分开（不同上下文、不同身份）
- **批准永远来自人**：分支保护 + code owner 审批不可豁免；Agent 的报告是输入，不是签字
- 评审发现要**反哺 CLAUDE.md**：同一类问题被审查标记第二次，预防性规则就写进项目记忆——让它下次在**写的时候**就被拦住，而不是审出来

### 度量：审查流程本身也要被审查

- Important 发现密度（每千行 diff）：监控代码质量趋势
- Agent 发现 → 人工确认率：太低说明在制造噪音，调政策；过高说明实现质量下滑，回到 Week 5 改仓库
- PR 周期时间：审查是否真的在加速而不是新瓶颈

---

## 小结

- AI 审查的优势是零边际成本的全面性（多视角 pass、跨文件一致性、对照规格）；意图、权衡、组织语境必须留给人
- 审查架构三件套：多 pass（单一视角聚焦）、Important/Nit 分级（有上限）、不报告清单（降噪）
- REVIEW.md 让审查标准成为版本化资产，改政策走代码评审
- 接入 PR 流程时守住职责分离：审查与实现分离、批准永远来自人、发现反哺 CLAUDE.md 形成预防闭环
