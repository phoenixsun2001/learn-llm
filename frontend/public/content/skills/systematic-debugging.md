# Systematic Debugging 系统化调试

bug 不是靠"灵光一现"修好的，而是靠**一套可重复的流程**逐步缩小范围。这个 Skill 把调试从"瞎猜乱改"变成"假设驱动的科学方法"。

## 为什么需要它

AI 调试时最常见的失败模式：
- **改了再试，试了再改**——没有假设，纯靠运气。
- **一次改好几处**——不知道是哪个改动起的作用。
- **只治症状**——压住了报错，根因还在。
- **过早下结论**——"我觉得是 X 的问题"，然后沿着错的路线走很久。

系统化调试用结构对抗这些倾向。

## 调试的五个阶段

### 1. 复现（Reproduce）

先让 bug **稳定复现**。不能稳定复现的 bug 几乎无法修。写下确切的复现步骤、输入、环境。

### 2. 隔离（Isolate）

用**二分法**缩小范围：
- 注释掉一半代码，bug 还在吗？
- 换一份输入，还触发吗？
- 哪个 commit 引入的？（git bisect）

目标：把"整个系统有问题"缩小到"这行/这段有问题"。

### 3. 假设（Hypothesize）

基于隔离结果，提出一个**具体的、可证伪的**假设："我认为是 X 为 null 导致的，因为……"。

不要说"可能是这个问题"——要说出**为什么**这么认为，以及**怎么证明错**。

### 4. 验证（Test）

用最小改动验证假设：
- 加一行日志/断点，看 X 是不是真的为 null。
- **一次只验证一个假设**，不要同时改多处。
- 如果假设错了，回到第 3 步提新假设，**不要**继续沿着错假设改。

### 5. 修复 + 回归（Fix & Verify）

确认根因后再改代码。改完：
- 原 bug 不复现了？
- 没有引入新问题？（跑相关测试）
- 同类问题别处还有吗？

## 反模式（一定要避免）

- ❌ 在没复现的情况下改代码。
- ❌ 一次改 5 处然后跑一次，绿了就提交（不知道为什么好）。
- ❌ 用 try/except 吞掉异常当"修复"。
- ❌ "我先随便改改试试"。

## 一句话

**调试是科学实验，不是猜谜**：复现 → 隔离 → 假设 → 验证 → 修复。每一步都有依据，而不是靠运气。
