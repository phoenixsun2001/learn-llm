## 学习目标

完成本章后，你将能够：

- 熟练使用 ZCode Agent 的提问入口和对话能力
- 精准地为任务补充上下文（引用文件、引用命令输出）
- 根据任务特点选择合适的执行模式和模型
- 调节推理强度以平衡质量与速度
- 理解一次优质提问的结构，让 Agent 一次做对

## ZCode Agent 是什么

ZCode Agent 是 ZCode 自研的默认智能体，也是新建任务时最直接的提问入口。你在同一个工作台里提出需求、补充上下文、引用文件、调用命令，并选择适合当前任务的模型和执行模式。

它的特点是「一站式」：不需要在多个面板间切换，从提出需求到看到结果，整个交互都在一个工作台内完成。这让它既能处理「帮我加个注释」这样的小请求，也能驱动「重构这个模块」这样的复杂长程任务。

## 提问入口与基本交互

### 新建任务

在左侧边栏新建任务后，工作台中央就是输入区。你可以直接用自然语言描述需求，ZCode Agent 会理解并开始工作。

```text
我在做一个 React 项目，user-service.ts 里的 fetchUser 函数没有处理网络超时，
请帮我加上超时重试逻辑，重试 3 次，每次间隔 1 秒。
```

### 多轮对话

提交首轮需求后，工作台会进入对话状态。你可以继续追问、调整方向或补充信息：

```text
（首轮）帮我给 api/ 目录下所有 controller 加上错误日志
（追问）很好，但是日志里请带上 request id，从 req.headers['x-request-id'] 取
（追问）再把日志级别从 info 改成 error
```

Agent 会保留对话上下文，基于已有改动继续迭代，而不是从零开始。

## 补充上下文的几种方式

上下文质量直接决定 Agent 的工作质量。ZCode 提供了几种补充上下文的方式。

### 方式一：引用文件

在工作区文件树中点击文件，即可把它作为上下文引用进当前对话。被引用的文件会高亮显示，Agent 会优先读取这些文件。

适用场景：你已经明确知道要修改或参考哪些文件。

```text
（引用 user-service.ts、user-service.test.ts）
帮我把 fetchUser 改造成支持取消请求，用 AbortController 实现，
并补充对应的测试用例。
```

### 方式二：描述代码位置

当你不确定确切文件，但知道功能位置时，可以用描述引导 Agent 自行定位：

```text
负责用户登录的那个文件，在收到错误响应时没有清理本地 token，
帮我找到并修复。
```

Agent 会结合代码搜索能力自行定位相关文件。

### 方式三：提供约束与规范

把项目约定、代码风格、接口契约作为上下文告诉 Agent，能让产出更符合团队标准：

```text
我们项目用 zod 做运行时校验，所有外部数据入口都要过 zod schema。
请按照这个规范，给 fetchUser 的返回值加上 zod 校验。
```

## 执行模式与模型选择

ZCode 允许你根据任务特点调整执行模式和所用模型，这是驾驭长程任务的关键。

### 模型选择

不同模型在能力、速度、成本上有差异。一般原则：

| 任务特点 | 推荐选择 |
|---------|---------|
| 复杂推理、架构设计、大范围重构 | 能力更强的旗舰模型 |
| 常规增删改、注释补全、格式调整 | 速度更快的模型 |
| 需要控制成本的大批量任务 | 性价比模型 |

在工作台顶部可以切换当前任务使用的模型。

### 执行模式

对于长程任务，你可以指定 Agent 的执行范围和自主程度。例如，是让它「一次性把能做的都做完」，还是「每完成一个关键步骤就暂停让你确认」。自主程度越高，Agent 推进得越快，但你介入的机会越少；反之则更可控。

## 推理强度

ZCode 允许调节 Agent 的**推理强度**（thinking effort）。这是一个重要的旋钮：

- **高推理强度**：Agent 在行动前会做更充分的思考、规划、方案对比，适合复杂问题、有歧义的需求、容易出错的操作。质量更高，但耗时更长。
- **低推理强度**：Agent 快速响应、直接行动，适合明确的、机械式的任务。速度更快。

选择建议：

```text
# 这类需求适合高推理强度——有多种实现方式，需要权衡
帮我设计一个支持多租户的权限模型，要考虑数据隔离和性能

# 这类需求适合低推理强度——意图明确，直接做
把这 30 个文件里的 var 都改成 const 和 let
```

## 一次优质提问的结构

让 Agent「一次做对」的关键，是把需求说清楚。一个好的提问通常包含四个要素：

```text
1. 目标：我要做什么
2. 上下文：涉及哪些文件 / 当前的实现是怎样的
3. 约束：必须遵守什么规范、不能破坏什么
4. 验收：怎样算完成
```

完整示例：

```text
[目标] 给 PaymentService.charge 方法增加幂等性支持
[上下文]（引用 payment-service.ts）当前每次调用都会发起扣款
[约束] 我们的幂等键是 clientRequestId，已存在于 request header；
       不能改变现有方法签名，只能新增可选参数
[验收] 同一个 clientRequestId 重复调用只扣款一次；
       补充单元测试覆盖「重复调用」和「并发调用」两种场景
```

养成这样提问的习惯，你会发现 Agent 的产出质量显著提升，返工次数大幅减少。

## 小结

ZCode Agent 是你与长程任务交互的核心入口。掌握上下文补充、执行模式和推理强度的调节，你就能让 Agent 在质量与速度之间找到最佳平衡点。
