# 上下文工程与规格驱动开发（CS146S Week 2）

CS146S 的第二周进入第二层「武装单个 Agent」。本周的洞察是一句话：**Agent 的能力上限由你给它的上下文、工具和约束决定，而非模型本身。** 同一个模型，喂给它不同的上下文，表现可以差出一个量级——所以 2026 年最重要的技能之一不再是「写提示词」，而是「设计上下文」。

本周四块内容：高级提示技巧、RePPIT 规格驱动框架、MCP 完整原理、工具设计的「Agent 人机工学」。

## 学习目标

完成本教程后，你将能够：

- 区分「提示工程」与「上下文工程」，理解上下文窗口是最稀缺的资源
- 用 RePPIT（Research → Propose → Plan → Implement → Test）框架把模糊需求翻译成 Agent 可执行的规格
- 说清 MCP（Model Context Protocol）的架构：Host / Client / Server 与三类原语
- 用「Agent 人机工学」的标准审视和改进一个工具定义

---

## 一、从提示工程到上下文工程

提示词工程优化的是**一句话怎么说**；上下文工程优化的是**模型在决策那一刻能看到什么**。后者包含前者，但范围大得多：

```text
┌────────────────── 上下文窗口（稀缺资源）──────────────────┐
│ 系统提示词（身份/准则/工具规范）                            │
│ 项目记忆：CLAUDE.md / AGENTS.md                            │
│ 对话历史：任务描述 + 用户的每次澄清                          │
│ 工具调用历史：读过的文件、跑过的命令、成败与输出              │
│ 检索注入：文档、issue、设计稿、网页内容                      │
└──────────────────────────────────────────────────────────┘
```

上下文工程的四条核心原则：

1. **每一个 token 都有成本**。无关的文件内容挤占有用的指令；模型对上下文中「 middle 部分」的注意力本来就弱（lost in the middle）。塞满 ≠ 更好。
2. **信息要放在离决策最近的地方**。任务相关的约束写进当次消息，稳定的项目约定才进 CLAUDE.md——按「变化频率」分层存放。
3. **为失败而设计**。好的上下文预判模型的常见误解，主动写清「不要做什么」（如：不要新建框架、不要改无关文件、不要跳过失败的测试）。
4. **让 Agent 自己维护上下文**。鼓励它把发现写进笔记/计划文件，长任务中定期回顾目标——而不是依赖它「记住」两万 token 前的约定。

### 高级提示技巧速查

| 技巧 | 适用场景 | 要点 |
|------|---------|------|
| 结构化分区 | 任何长任务 | 用 XML/Markdown 标签分区：`<context>`、`<task>`、`<constraints>`，模型检索更准 |
| Few-shot 示例 | 有明确格式要求 | 给 2~3 个「输入→期望输出」样例，比形容词描述有效得多 |
| 思考空间 | 复杂推理/规划 | 要求先产出计划再动手；显式给「thinking budget」 |
| 负面约束 | 防跑偏 | 明确列出禁止项；只说「要什么」模型会自行脑补「还可以做什么」 |
| 自我校验 | 完成标准 | 要求 Agent 自述「我怎么验证这做对了」，做不到就说明任务规格不清 |

## 二、RePPIT：规格驱动开发的五步框架

RePPIT 是本周的重头戏：一套把「产品需求」翻译成「Agent 可执行规格」的工作流。名字来自五个阶段：

```text
Research → Propose → Plan → Implement → Test
 (调研)     (提案)     (计划)    (实现)      (测试)
   ↑____________________________________________|
              失败与发现回流，重新进入循环
```

| 阶段 | 人的动作 | Agent 的动作 | 产出工件 |
|------|---------|-------------|---------|
| **Research** | 提供业务背景、指出相关系统 | 读代码、读文档、摸清现状与约束 | 现状摘要 + 约束清单 |
| **Propose** | 判断方向对不对、砍范围 | 提出方案选项与权衡（A vs B） | 一页纸提案：目标、非目标、选型理由 |
| **Plan** | 质询计划：漏了什么？风险在哪？ | 列改动文件、顺序、验证方式 | 计划文档（改动清单 + 测试证明） |
| **Implement** | 在关键节点确认 | 按计划小步实现，每步可验证 | 代码 + 提交历史 |
| **Test** | 验收：是否解决真问题 | 跑测试、构建、截图自证 | 绿灯记录 + 验收对照 |

三个关键认识：

1. **前两个 R 和 P 最值钱**。直接说「帮我做个 XX 功能」然后盯着 Agent 写代码，是把五个阶段压缩成两个——省下的时间会在 Implement 阶段以返工的形式加倍偿还。规格的质量决定实现的效率。
2. **每个阶段都有独立工件**。提案、计划是可以被评审、被修正、被复用的实体，而不是聊天记录里的一闪念。这与 AI 原生 SDLC 的「工件链」（intent.md → spec.md → plan.md）是同一思想。
3. **人是方向的裁判，不是代码的监工**。每个阶段切换处设一个判断点：接受这个工件，还是打回？人的注意力花在 5 个判断点上，而不是 500 行 diff 上。

> 💡 规格驱动的本质：**把「想到写清楚」的成本前置**。对独立开发者，最小可行版就是开工前强制自己写一段三行规格：要什么、不要什么、怎么算完成。

## 三、MCP：给 Agent 接上世界的标准接口

MCP（Model Context Protocol）是 Anthropic 发起、现已成为行业事实标准的协议，解决的问题是：**工具与数据源不必为每个 Agent 各写一遍集成**。写一次 MCP Server，任何支持 MCP 的 Agent 都能用。

### 架构：三个角色

```text
┌─────────────┐   ┌─────────────┐   ┌─────────────────┐
│  MCP Host    │   │  MCP Client │   │  MCP Server      │
│ (Claude Code │◄──┼─(1:1 连接)──┼──►│ (GitHub/数据库/   │
│  /你的Agent) │   │             │   │  内部API的封装)   │
└─────────────┘   └─────────────┘   └─────────────────┘
```

- **Host**：用户面对的 Agent 应用（Claude Code、ZCode、IDE 插件……）
- **Client**：Host 内部与某个 Server 保持 1:1 连接的中间层
- **Server**：把某个外部系统的能力封装成标准接口的轻量服务——可以是官方的（GitHub、Slack、Postgres），也可以是你为自家系统写的

### 三类原语

| 原语 | 是什么 | 类比 |
|------|--------|------|
| **Tools** | 模型可主动调用的动作（创建 issue、查询数据库） | 函数调用 |
| **Resources** | 可被读取的数据（文件、记录、schema） | GET / 文件系统 |
| **Prompts** | 预制的提示词模板 | 快捷指令 |

MCP 的深远意义在于**分层的生态**：工具的建设者（写 Server 的人）与 Agent 的使用者（配置 Host 的人）解耦了。Week 9 会看到这个协议在组织级的延伸——MCP portals 把全公司的工具目录集中起来统一授权。

## 四、工具设计的 Agent 人机工学

「人机工学」（ergonomics）原本研究工具怎么适合人的身体；这里研究**工具怎么适合模型的「认知」**。课程给出的判断标准：

1. **工具描述是给模型看的 API 文档**。模型完全依据 description 决定何时用、怎么用。写清楚「什么时候该用我、什么时候不该用」，比罗列参数更重要。
2. **参数少而扁平**。每个额外参数都是一次出错机会；能推断的就不要让模型填。
3. **返回值可行动**。错误信息要告诉模型「错在哪、该怎么改」，而不是堆栈dump。`old_string not unique (found 3 matches)` 就远好于 `AssertionError`。
4. **一次调用一个意图**。「搜索并读取并修改」三合一的工具让模型难以判断失败发生在哪一步。
5. **故障要窄**。工具失败应当局部化——一个失败的调用不该污染整个会话状态。

> 💡 自检方法：把你的工具定义给一个**没见过实现**的同事（或另一个模型）看，只凭 description 和返回样例，能否答对「什么时候用、怎么调用、失败了怎么办」。答不对，就还没到生产标准。

## 小结

- 上下文工程 > 提示工程：优化的是模型决策那一刻能看到的信息全集，每个 token 都是稀缺资源
- RePPIT 五阶段（Research→Propose→Plan→Implement→Test）把模糊需求变成可执行规格；**前两个阶段最值钱**，规格质量决定实现效率
- 每个阶段留下可评审的独立工件，人只在工件切换处做判断——这与 AI 原生 SDLC 的工件链一脉相承
- MCP 用 Host/Client/Server 三层 + Tools/Resources/Prompts 三原语，把「接工具」变成一次建设、处处可用
- 工具的 Agent 人机工学五条：描述即文档、参数少而扁平、返回可行动、单一意图、故障要窄
