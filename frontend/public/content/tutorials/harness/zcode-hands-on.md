## 实战任务：为工具函数补全类型与注释

我们用一个贴近真实开发的任务：给一批工具函数补充 TypeScript 类型注解和 JSDoc 注释。这类任务意图明确、范围可控、易于验收，非常适合作为 Agent 协作的入门实战。

### 任务背景

假设你的项目里有一个 `src/utils/format.ts`，包含若干格式化函数，但缺少完善的类型和文档。示例：

```typescript
// 现状：类型缺失、无注释
export function formatPrice(num) {
  return '¥' + num.toFixed(2)
}

export function truncate(str, len) {
  return str.length > len ? str.slice(0, len) + '...' : str
}
```

### 第一步：用四要素结构组织提问

打开 ZCode，新建任务，先引用目标文件 `src/utils/format.ts`，然后按四要素写下需求：

```text
[目标] 为 src/utils/format.ts 中所有函数补全 TypeScript 类型注解和 JSDoc 注释
[上下文]（已引用 format.ts）这些是项目通用的格式化工具函数
[约束] 不要改变函数的运行时行为和函数名；
       类型要尽量精确（避免滥用 any）；
       JSDoc 用中文，说明参数、返回值和一个使用示例
[验收] npm run build（或 tsc --noEmit）无类型错误
```

> 为什么强调四要素？因为「补全类型」这类任务，如果不说清约束，Agent 可能给所有参数都标 `any`——技术上不报错，但毫无价值。明确「避免滥用 any」就避免了这种「假完成」。

### 第二步：观察 Agent 执行

提交后，Agent 会自主推进。重点观察它的**工作过程**，这是培养手感的关键：

- **它读了什么**：是否正确读取了 format.ts 的全部函数
- **它怎么决策**：对于 `num.toFixed(2)`，它能否推断出 `num: number`；对于可选参数，是否用了 `?`
- **它如何验收**：是否主动运行了类型检查来确认无误

Agent 改完后，预期产出类似：

```typescript
/**
 * 将数字格式化为人民币价格字符串，保留两位小数。
 * @param num - 要格式化的数字
 * @returns 形如 "¥123.45" 的价格字符串
 * @example
 * formatPrice(123.4) // => "¥123.40"
 */
export function formatPrice(num: number): string {
  return '¥' + num.toFixed(2)
}
```

### 第三步：验收与迭代

任务完成后，**不要急着接受**，先做验收：

1. **看类型检查**：Agent 是否真的跑了 `tsc`，结果如何
2. **抽查产出**：随机看两个函数，类型是否精确、注释是否准确
3. **边界情况**：`truncate` 的 `len` 是否被标为可选或有默认值？空字符串会不会出问题？

如果发现问题，直接在对话里追加要求迭代：

```text
（追问）truncate 的 len 参数应该是必填的，而且要处理 len <= 0 的边界，
请加上类型守卫并在 JSDoc 里说明这一点。
```

Agent 会基于已有改动继续修正，而不会从头再来。这就是多轮对话迭代的力量。

## 常见踩坑与对策

实战中最容易遇到的几个问题：

| 踩坑 | 现象 | 对策 |
|------|------|------|
| 约束太模糊 | Agent 用 `any` 敷衍 | 明确写「禁止 any，用具体类型」 |
| 缺少验收标准 | 不知道算不算完成 | 给出可执行的命令（tsc、test） |
| 上下文不足 | Agent 改错文件 | 主动引用目标文件 |
| 一次要求太多 | 改动混乱难验收 | 一次只聚焦一个目标 |

## 进阶练习：自己设计一个任务

完成上述实战后，用同样的方法尝试一个你自己工作中的小任务。建议从这些方向挑选：

- 为一个模块的公开函数补全单元测试
- 把某个文件里的 `var` 重构为 `const/let`
- 统一一组 API 的错误返回格式

关键是用**四要素结构**写下需求，并给出**可执行的验收命令**。养成这个习惯，你就掌握了和 Agent 高效协作的核心。
