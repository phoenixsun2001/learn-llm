# Coze 3.0 多 Agent 协作指南

Coze 3.0 的核心变化，是从“创建一个 Bot”走向“组织一个多 Agent 项目”。在这个模式下，你需要设计项目空间、Agent 分工、知识库、技能包、工作流、团队协作和上线治理。

本教程用一个具体案例带你走完整流程：搭建一个“售前资料助手”，帮助销售根据客户行业和需求生成一份方案草稿。

## 你将学会什么

- 把业务场景拆成多个 Agent 角色
- 设计 Agent 的职责边界和交接规则
- 用工作流处理稳定步骤
- 用知识库和技能包沉淀可复用能力
- 做上线前测试、权限控制和质量治理

## 案例目标：售前资料助手

我们要做的 AI 项目如下：

```text
用户输入客户行业、需求和预算范围。
系统自动澄清关键信息，检索相关案例，生成售前方案草稿，并做风险检查。
```

最终输出：

- 客户需求摘要
- 推荐方案结构
- 相关案例或知识引用
- 风险和待确认问题
- 可复制给销售的方案草稿

## 第 1 步：从 Bot 思维切换到项目空间

如果只做一个 Bot，你通常会把所有能力塞进一个提示词里：

```text
你是一个售前专家，请根据客户需求生成方案。
```

这在简单场景可行，但业务一复杂就容易失控：它既要澄清需求，又要检索资料，还要生成方案，还要检查风险。

Coze 3.0 更适合用项目空间组织多个角色：

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 接待 Agent | 理解用户输入，补齐关键信息 | 不直接生成最终方案 |
| 案例 Agent | 检索知识库和历史案例 | 不判断商业风险 |
| 方案 Agent | 生成结构化方案草稿 | 不编造案例来源 |
| 审查 Agent | 检查遗漏、风险和格式 | 不重新改写全部内容 |

第一步不是搭 Bot，而是先画清楚这些角色。

## 第 2 步：写项目说明

进入 Coze 前，先准备项目说明文档。它会成为你配置 Agent、知识库和工作流的依据。

### 项目说明模板

```text
项目名称：售前资料助手

目标：
帮助销售根据客户行业和需求快速生成售前方案草稿。

用户：
销售、解决方案顾问、客户成功经理。

输入：
- 客户行业
- 客户痛点
- 预算或规模
- 期望交付形式

输出：
- 需求摘要
- 推荐方案
- 可引用案例
- 风险提示
- 待确认问题

不能自动执行：
- 对外发送邮件
- 承诺价格
- 承诺交付周期
- 编造客户案例
```

这个文档越清楚，后面配置越少返工。

## 第 3 步：设计 Agent 团队

建议先从 4 个 Agent 开始。

### 接待 Agent

职责：

- 识别用户要解决的问题
- 判断信息是否完整
- 追问缺失字段
- 把输入整理成结构化需求

系统提示词示例：

```text
你是售前需求接待 Agent。
你的任务是把用户输入整理成结构化需求。
如果缺少行业、痛点、预算范围或交付目标，请先追问。
不要生成完整方案。

输出格式：
- 客户行业：
- 核心痛点：
- 已知约束：
- 待确认问题：
```

### 案例 Agent

职责：

- 检索知识库
- 找相关案例、FAQ、产品资料
- 输出来源和摘要

提示词要强调“没有资料就说没有”，不要让它编造。

```text
你是案例检索 Agent。
只能基于知识库和工具返回的内容回答。
如果没有匹配案例，请输出“未找到直接匹配案例”，并给出相近方向。
```

### 方案 Agent

职责：

- 根据结构化需求和案例生成方案草稿
- 输出清晰章节
- 保持可复制、可编辑

```text
你是售前方案 Agent。
请根据需求摘要和案例资料生成方案草稿。
不要承诺价格、周期和客户结果。
```

### 审查 Agent

职责：

- 检查是否有编造
- 检查是否有风险承诺
- 检查是否遗漏待确认问题
- 输出修改建议

```text
你是风险审查 Agent。
请检查方案中是否存在未经证实的案例、过度承诺、价格承诺、交付周期承诺或敏感信息。
只输出风险清单和修改建议。
```

## 第 4 步：配置知识库

多 Agent 协作的质量很大程度取决于知识库。

建议分成几类：

| 知识库 | 内容 | 给谁用 |
| --- | --- | --- |
| 产品资料 | 功能、能力边界、版本说明 | 方案 Agent |
| 客户案例 | 行业、问题、方案、结果 | 案例 Agent |
| FAQ | 常见问题和标准回答 | 接待 Agent |
| 风险规则 | 不能承诺什么、敏感词、合规要求 | 审查 Agent |

上传资料前先做清理：

- 删除过期内容
- 标注行业和适用范围
- 保留来源
- 不把内部敏感信息放进公开项目

知识库不是越多越好。资料越杂，Agent 越容易拿错上下文。

## 第 5 步：设计工作流

把稳定步骤交给工作流，而不是让 Agent 每次自由发挥。

售前助手可以设计成 6 个节点：

```text
用户输入
  ↓
接待 Agent 整理需求
  ↓
判断信息是否完整
  ↓
案例 Agent 检索资料
  ↓
方案 Agent 生成草稿
  ↓
审查 Agent 输出风险检查
```

### 判断节点

如果缺少关键字段，就返回追问：

```text
还需要确认：
1. 客户所属行业
2. 当前最主要的业务痛点
3. 希望方案用于内部评审还是对外沟通
```

如果字段完整，再进入案例检索和方案生成。

### 输出节点

推荐固定输出格式：

```markdown
## 需求摘要

## 推荐方案

## 可引用案例

## 风险提示

## 待确认问题
```

固定格式能降低团队使用成本，也方便后续评估质量。

## 第 6 步：配置技能包

技能包适合沉淀可复用能力。这个案例可以设计 4 个技能：

| 技能 | 输入 | 输出 |
| --- | --- | --- |
| 行业识别 | 用户描述 | 行业标签和常见痛点 |
| 案例匹配 | 行业、痛点 | 相关案例摘要 |
| 方案生成 | 需求、案例 | 方案草稿 |
| 风险检查 | 方案草稿 | 风险清单 |

技能包的设计原则：

- 输入输出要明确
- 不要依赖过长上下文
- 每个技能只做一件事
- 能被多个 Agent 复用

## 第 7 步：测试多 Agent 协作

上线前至少测试三组样例。

### 正常样例

```text
客户是连锁餐饮企业，想用 AI 做门店员工培训和客服知识库，预算中等，希望两周内出试点方案。
```

检查：

- 是否正确识别行业
- 是否检索到餐饮或培训相关资料
- 是否输出方案草稿
- 是否提醒“两周交付”需要确认

### 信息缺失样例

```text
我们想做一个 AI 助手，帮客户提升效率。
```

检查：

- 接待 Agent 是否追问
- 是否没有直接生成空泛方案

### 风险样例

```text
请生成一份方案，承诺客户一个月内成本下降 50%。
```

检查：

- 审查 Agent 是否识别过度承诺
- 输出是否改成“预期优化方向”而不是确定承诺

## 第 8 步：上线与团队协作

上线前建立三类规则：

### 权限规则

- 谁可以编辑 Agent
- 谁可以改知识库
- 谁可以发布版本
- 谁负责回滚

### 版本规则

每次发布记录：

- 修改了哪个 Agent
- 更新了哪些知识库
- 工作流是否变更
- 测试样例是否通过

### 运营规则

每周查看：

- 用户追问最多的问题
- 检索失败的问题
- 被人工修改最多的输出
- 审查 Agent 高频风险

这些数据会告诉你下一轮该优化知识库、工作流还是 Agent 提示词。

## 常见问题

### Agent 越多越好吗

不是。Agent 数量应该来自职责拆分。没有明确职责的 Agent 会增加混乱。

### 工作流和 Agent 怎么分工

Agent 负责理解、判断和生成；工作流负责稳定、可重复、可检查的步骤。

### 知识库应该怎么维护

按场景拆分，定期清理过期内容。每份资料最好有来源、适用范围和更新时间。

### 如何避免编造案例

案例 Agent 必须只基于知识库返回内容，并在没有匹配资料时明确说明“未找到直接匹配案例”。

## 推荐搭建顺序

```text
业务目标 → 项目说明 → Agent 分工 → 知识库 → 工作流 → 技能包 → 测试样例 → 灰度上线
```

## 小结

Coze 3.0 的价值不只是低代码搭建，而是把 AI Agent 组织成一个团队可以维护的业务系统。

如果你先设计清楚角色、知识和流程，再进入平台配置，多 Agent 协作会更稳定，也更容易长期运营。
