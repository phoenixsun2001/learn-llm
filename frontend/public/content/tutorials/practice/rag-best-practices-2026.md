## 什么是 RAG

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种将信息检索与大型语言模型结合的技术架构。它的核心思想是：在 LLM 生成回答之前，先从外部知识库中检索最相关的文档片段，将这些片段作为上下文注入到 Prompt 中，让模型基于检索到的"事实依据"来生成回答。

```
┌─────────────────────────────────────────────────────────┐
│                    RAG 架构（2026）                       │
│                                                         │
│  用户提问                                               │
│     ↓                                                   │
│  1. Query 改写 & 扩展（Query Construction）              │
│     ├── HyDE（假设文档嵌入）生成虚拟答案                  │
│     ├── Multi-Query 生成多个检索视角                     │
│     └── Query 分解为子问题                              │
│     ↓                                                   │
│  2. 混合检索（Hybrid Retrieval）                        │
│     ├── 稠密检索（Dense）：语义嵌入向量相似度             │
│     ├── 稀疏检索（Sparse）：BM25 / SPLADE 关键词匹配     │
│     └── 图谱检索（Graph）：知识图谱实体关系              │
│     ↓                                                   │
│  3. 重排序 & 过滤（Reranking & Filtering）               │
│     ├── Cross-Encoder 精排                               │
│     ├── 元数据过滤（时间、来源、权限）                    │
│     └── 多样性优化（MMR）                                │
│     ↓                                                   │
│  4. 上下文组装（Context Assembly）                       │
│     ├── 文档排序 & 截断（Top-K，窗口限制）               │
│     ├── 引用标注（Citation）                             │
│     └── Prompt 模板注入                                 │
│     ↓                                                   │
│  5. LLM 生成（Generation）                              │
│     ├── 基于检索上下文生成回答                           │
│     ├── 引用溯源 & 事实校验                              │
│     └── 置信度评估（不确定时触发补充检索）                │
└─────────────────────────────────────────────────────────┘
```

与纯 LLM 相比，RAG 解决了三大核心痛点：
- **知识时效性**：LLM 的训练数据有截止日期，RAG 可以接入实时更新的知识库
- **幻觉问题**：通过提供可验证的来源文档，显著降低模型编造事实的概率
- **领域专业性**：无需微调模型，只需构建领域知识库即可获得专业级回答

## 2026 年 RAG 关键趋势

### 1. Agentic RAG（智能体 RAG）

传统的单次检索-生成流程正在被**多步推理 + 工具调用**的 Agent 模式取代。Agentic RAG 的关键特征：

- **自适应检索**：系统根据问题复杂度自动决定检索轮次，简单问题 1 轮，复杂问题多轮迭代
- **工具编排**：检索不再是唯一的信息源——Agent 可以同时查询数据库、调用 API、读取文件
- **自我修正**：当生成结果置信度不足时，自动触发补充检索或向用户追问澄清

```python
# Agentic RAG 的简化控制流
def agentic_rag(query, max_rounds=3):
    context = []
    for round in range(max_rounds):
        docs = retrieve(query, context)       # 检索
        answer = generate(query, docs)         # 生成
        confidence = evaluate(answer, docs)    # 评估
        if confidence > THRESHOLD:
            return answer, docs
        query = refine_query(query, answer)    # 改写查询
    return answer, docs  # 达到最大轮次，返回最佳结果
```

### 2. 多模态 RAG

2026 年的 RAG 系统不再局限于文本。多模态 RAG 支持对**图片、表格、图表、代码、音频**的统一检索和生成：

- **视觉 RAG**：ColPali / ColQwen 等视觉语言模型直接对 PDF 页面图像进行嵌入，无需 OCR 和文本提取
- **表格 RAG**：结构化数据使用独立的表格嵌入模型，保留数值关系
- **代码 RAG**：代码库级别检索，理解函数调用关系和依赖图

### 3. 长上下文 + RAG 的融合

随着 Gemini 2.5 Pro（1M tokens）和 Claude 4（200K tokens）等长上下文模型的普及，2026 年的最佳实践不再是"RAG vs 长上下文"二选一，而是两者的**策略性组合**：

| 场景 | 推荐方案 |
|------|----------|
| 少量文档（< 50 页） | 直接使用长上下文，无需 RAG |
| 中等规模（50-500 页） | RAG 粗筛 + 长上下文精读 |
| 大规模语料（> 500 页） | 多级 RAG + 分而治之（Map-Reduce）|
| 实时数据（新闻、股价） | RAG 必须，因为模型训练数据滞后 |

## 生产级 RAG 最佳实践

### 1. 分块策略（Chunking）

分块是 RAG 系统中最被低估的设计决策。错误的分块策略会导致检索召回率大幅下降。

**2026 年推荐的分块方案**：

| 策略 | 适用场景 | 典型大小 | 重叠 |
|------|----------|----------|------|
| **语义分块（Semantic）** | 技术文档、学术论文 | 按段落/章节边界 | 1-2 句 |
| **递归分块（Recursive）** | 通用文本 | 512-1024 tokens | 10-15% |
| **句子窗口（Sentence Window）** | FAQ、对话记录 | 单句检索，窗口扩展 | 前后各 3-5 句 |
| **层级分块（Hierarchical）** | 长篇结构化文档 | 父块 2048 + 子块 256 | 父子关联 |
| **Agentic 分块** | 动态复杂场景 | LLM 自主决定边界 | 自适应 |

**关键原则**：
- 不要让语义单元被切断（一句话或一段代码横跨两个 chunk）
- 保留足够的重叠以维持上下文连贯性
- 为每个 chunk 保留元数据：来源文档、页码、章节标题、时间戳

### 2. 嵌入模型选型

2026 年嵌入模型的关键考量已经不仅是 MTEB 排行榜分数：

| 模型 | 维度 | 最大 Token | 适用场景 | 备注 |
|------|------|------------|----------|------|
| `voyage-3-large` | 2048 | 32000 | 长文档、技术内容 | 2026 年综合最佳 |
| `text-embedding-3-large` | 3072/256 | 8191 | 通用场景、多语言 | 支持 Matryoshka 降维 |
| `stella_en_1.5B` | 1024 | 8192 | 英文技术文档 | 开源，可本地部署 |
| `jina-embeddings-v3` | 1024 | 8192 | 多语言、代码 | 支持任务特定 LoRA |
| `ColQwen2.5` | 128 | 768（图像） | 视觉 RAG / PDF | 多模态 Late Interaction |

**选型建议**：
- **有预算**：`voyage-3-large` + Matryoshka 降维到 512 维，兼顾质量和存储成本
- **开源自主**：`stella_en_1.5B`（英文）或 `bge-m3`（多语言）
- **多模态需求**：`ColQwen2.5` 或 `ColPali` 用于 PDF 密集型场景

### 3. 检索策略

**混合检索是 2026 年的标配**，而非可选项：

```
混合检索 = α × 稠密检索（语义相似度）+ (1-α) × 稀疏检索（关键词匹配）

α 通常取 0.3-0.7，需要根据实际数据调优
```

**高级检索模式**：

- **HyDE（假设文档嵌入）**：先让 LLM 生成一个虚拟答案，用虚拟答案的嵌入去检索真实文档。对于"how-to"类问题效果显著
- **Multi-Query**：将原始问题改写为 3-5 个不同角度的查询，合并去重后返回。适合歧义性问题
- **Self-Query**：LLM 从问题中提取结构化过滤条件（时间范围、文档类型等），结合语义检索
- **时间衰减加权**：对时效性敏感的场景（如新闻、股价），检索时根据文档发布时间施加衰减权重

### 4. 重排序（Reranking）

检索 20-50 个候选 → 重排序 → 保留 Top 5-10 输入 LLM。

| 重排序器 | 延迟 | 效果 | 适用场景 |
|----------|------|------|----------|
| `cohere-rerank-v3` | ~100ms | ★★★★★ | 英文，最佳精度 |
| `bge-reranker-v2-m3` | ~50ms | ★★★★☆ | 多语言，开源 |
| `jina-reranker-v2` | ~80ms | ★★★★☆ | 多语言，代码友好 |
| LLM-as-Reranker | ~500ms | ★★★★★ | 高价值场景，成本高 |
| 无重排序（直接 Top-K） | 0ms | ★★★☆☆ | 对延迟极敏感的场景 |

**何时可以跳过重排序**：
- 检索结果本身就是精确匹配（如 ID 查找）
- 延迟要求 < 200ms 且检索质量已经很好
- 使用 ColBERT 风格的 Late Interaction 模型（检索时已完成精细匹配）

### 5. 评估与监控

2026 年的 RAG 评估已经从"看看效果如何"进化为**持续自动化评估管线**：

**三层评估体系**：

```
Layer 1: 检索质量
├── Recall@K：相关文档是否在 K 个候选中
├── MRR（Mean Reciprocal Rank）：第一个相关文档的排名
└── NDCG@K：考虑排序位置的相关性评分

Layer 2: 生成质量
├── Faithfulness：回答是否忠实于检索文档（幻觉检测）
├── Answer Relevance：回答是否切题
└── Context Utilization：是否合理利用了检索到的上下文

Layer 3: 端到端质量
├── 用户满意度（👍/👎 反馈）
├── 任务完成率（用户是否得到了想要的答案）
└── 引用准确率（回答中的引用是否指向正确的来源）
```

**推荐工具栈**：
- **RAGAS**（开源）：自动化 RAG 评估框架，支持合成测试数据
- **LangSmith / Braintrust**：RAG 管道的可观测性和 A/B 实验
- **DeepEval**：单元测试风格的 RAG 评估，可集成到 CI/CD

## 常见陷阱与对策

### 陷阱 1：分块过大或过小

- **过大（> 2000 tokens）**：检索到的 chunk 包含过多无关信息，稀释了关键内容，浪费上下文窗口
- **过小（< 100 tokens）**：语义信息不完整，嵌入向量质量差，召回率骤降
- **对策**：512-1024 tokens 是经过大量实践验证的"甜区"；对特定领域进行分块消融实验

### 陷阱 2：忽视 Query 改写

用户输入的自然语言查询往往不适合直接用于向量检索：
- "那个蓝色的按钮怎么用" → 应改写为 "设置页面中蓝色提交按钮的操作方法"
- 口语化、指代不明、缺少上下文

**对策**：使用 LLM 进行 Query Rewriting，将对话上下文和用户意图编码进检索查询。

### 陷阱 3：上下文窗口装填不当

检索到的文档并非"越多越好"：
- 过多无关文档会分散 LLM 注意力（Lost in the Middle 效应）
- 相关文档被挤到上下文末尾可能被模型忽视
- **对策**：将最重要的文档放在上下文的最前面和最后面；总上下文控制在模型窗口的 60-70%

### 陷阱 4：缺少引用溯源

用户无法判断回答的可信度：
- **对策**：每个事实性陈述都应标注来源，提供可点击的引用链接；无法找到来源的陈述应标注为"模型推断"
