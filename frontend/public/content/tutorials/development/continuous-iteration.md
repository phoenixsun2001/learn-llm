系统上线不是终点，而是产品的起点。真正拉开差距的是上线之后：能不能安全地频繁发版？出问题几分钟能恢复？怎么在用户抱怨之前发现异常？这三件事合起来叫**可持续迭代**——本路径的最后一篇，也是把前面所有环节串成闭环的一篇。

## 你将学到

- 版本策略：语义化版本与"可回滚的发版"
- 灰度/蓝绿/滚动：三种发布方式与选择
- 回滚预案：回滚点怎么留、怎么练
- 监控告警的最小闭环：日志、健康、指标
- 一个真实复盘：本平台一次完整的"更新-验证-回滚点"流程

## 版本策略：先让每次发布"有名字"

- **语义化版本**（`v1.4.2`：主版本.功能.修复）：对外产品用它，用户能看懂升级含义。
- **不可变产物标识**（镜像 tag 用 commit SHA）：CI/CD 的地基——"重新部署上周三那个版本"必须指向唯一确定的镜像，而不是"最新的"。
- **CHANGELOG**：每次发版记三行（新增/修复/破坏性变更），未来的你会感谢现在的你。

纪律只有一条：**生产环境跑的每个东西，都能回答"你是哪个版本、从哪次构建来的"**。

## 三种发布方式

| 方式 | 做法 | 代价 | 适合 |
|------|------|------|------|
| **全量替换** | 停旧 → 起新 | 秒级中断 | 内部工具、允许维护窗口 |
| **蓝绿** | 新版本整套起好 → Nginx 切流量 → 旧版保留待命 | 双倍资源（期间） | 需要秒级回退的关键服务 |
| **灰度（金丝雀）** | 5% → 25% → 100% 逐步放量 | 需要流量分流与观测 | 用户量大的对外服务 |

Nginx 灰度的最小实现：

```nginx
# 按 cookie 分流：带 canary 标记的用户进新版本
split_clients "${remote_addr}${http_user_agent}" $backend {
    5%   canary_backend;
    *    stable_backend;
}
```

选择建议：**从全量替换起步**（个人/小团队足够），用户多了先加蓝绿（回退快），再演进灰度（风险面最小）。

## 回滚：不是方案，是肌肉记忆

回滚要满足三个"能"：

1. **能快速**：镜像按 SHA 留存在仓库（上一章 CI 已做），回滚 = `docker compose` 指回旧 tag + `up -d`，两分钟内完成。
2. **能放心**：**数据变更要向后兼容**——新版本可以加字段，别删旧字段；删字段放到"确认不回滚"之后。这是"敢回滚"的真正前提。
3. **能演练**：预发环境每季度真回滚一次。没演练过的回滚预案是装饰品。

## 监控告警：最小闭环

不用一上来就上 Prometheus 全家桶，最小闭环只有三层：

```text
1. 存活   → /health 端点 + uptime 监控（UptimeRobot 等免费即可）
2. 日志   → docker logs / 集中到文件，出错能 grep 到现场
3. 关键指标 → 每请求日志记（状态码、耗时、模型版本）；QPS/错误率周报一眼扫
```

告警两条军规：**只告需要人处理的**（否则一周后全员屏蔽告警）；**每条告警附带 runbook 链接**（"收到这个告警 → 打开这个文档 → 按步骤处理"）。

容器侧的基础配置（compose）：

```yaml
services:
  backend:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8400/health"]
      interval: 30s
      retries: 3
    restart: unless-stopped        # 崩了自动拉起，同时告警跟进根因
    logging:
      options: { max-size: "10m", max-file: "3" }   # 防日志写爆磁盘
```

## 真实复盘：一次完整的更新流程

以本平台的一次线上更新为例，"可持续迭代"长这样：

1. **发布前**：CI 已产出带 SHA 的镜像；备份当前挂载内容（`content/`、数据目录）到部署机——**回滚点 +1**。
2. **发布中**：构建新镜像 → 传输到部署机 → `docker compose up -d` 重建容器（秒级窗口）。
3. **发布后验证**：容器健康（`docker ps`/healthcheck）、核心路径冒烟（首页、API、新功能端点）、日志无异常——**验证是发布的一部分，不是可选项**。
4. **异常处理**：发现问题 → 指回旧 SHA 镜像 `up -d` → 恢复备份内容 → 复盘根因。全程两分钟级。

把这套动作写成一页 runbook 放进仓库（本平台的 `deploy.sh` + 部署文档即是雏形），迭代就从"个人手艺"变成了"团队资产"。

## 典型场景

- **场景 A：AI 功能更新影响效果评估。** 灰度 5% 用户跑两天，对比新旧版本的错误率/满意度指标，再决定放量——AI 行为变化比代码 bug 更隐蔽，灰度是唯一的安全网。
- **场景 B：深夜上线翻车。** 有了 SHA 镜像 + 数据兼容纪律，回滚两分钟；没有的话，通宵修 bug 还不一定修得好。差别全在发布前的准备。
- **场景 C：从"上线即失联"到"上线即观测"。** 加 healthcheck + 存活监控 + 请求日志三件套，一晚上配置完成，从此用户还没发现问题时你的手机已经响了。

## 小结

可持续迭代 = **版本可标识 × 发布可控制 × 回滚可演练 × 异常可发现**。全链路至此闭环：从产物思维（构建打包）到容器化、上线、自动化，最终回到"安全地变"这个软件工程的永恒主题。AI 让写代码变快了，但生产可用性与迭代纪律，仍然是区分玩具与产品的那条线。
