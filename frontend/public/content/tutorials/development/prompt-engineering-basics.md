同样是 GLM 或 Claude，有人用来写代码、做分析、跑自动化，觉得它无所不能；有人却抱怨它答非所问、胡编乱造。差距往往不在模型本身，而在**你怎么提问**。

Prompt 工程（Prompt Engineering）就是研究如何更有效地向大语言模型下达指令的学问。它不是玄学，而是一套可复用、可迭代的方法。这篇教程带你从一个只会打"帮我写一下"的新手，成长为能稳定产出预期结果的 Prompt 作者。

## 你将学到

- 理解为什么同一个模型，换个问法结果天差地别
- 掌握 5 条核心原则：清晰具体、给角色与上下文、分解任务、提供示例、指定输出格式
- 识别并避开常见坑：模糊指令、矛盾约束、让模型猜
- 会用 4 种主流模式：Zero-shot、Few-shot、Chain-of-Thought、角色扮演
- 能在真实开发场景里（抽取、分类、生成）写出可靠的 Prompt

## 为什么提示词决定一切

大语言模型本质上是一个**根据上文预测下一个 token** 的概率机器。它没有"意图理解"，只有"模式匹配"。你给的上文（Prompt）决定了它激活哪部分知识、走哪条推理路径。

举个极端对比。同一个模型：

```text
差：写首诗
好：以"秋雨"为题，写一首五言绝句，押 an 韵，风格仿王维，输出四句，不要任何解释。
```

差的版本，模型只能猜你要古体还是现代、要长短、要什么情绪——猜错概率极高。好的版本，把每一项约束都钉死，模型几乎只能按你想要的方式输出。**Prompt 工程的本质，就是把"让模型猜"降到最低。**

## 五条核心原则

### 原则一：清晰且具体

模糊是大忌。每一条指令都应该能被一个第三人独立执行而不产生歧义。要明确：**任务是什么、输出什么、有什么约束**。

```text
差：帮我总结一下这篇文章
好：将下面这篇 800 字的文章总结为 3 个要点，每个要点不超过 30 字，使用中文，用项目符号列出，不要复述原文。文章：……
```

### 原则二：给角色和上下文

告诉模型"你是谁""你面对的是谁""在什么场景下"。角色会激活模型内化得更深的领域知识和语气。

```text
差：解释什么是闭包
好：你是一位有 10 年经验的 JavaScript 工程师，正在向一个刚学完 HTML/CSS 的新手解释"闭包"。请用 200 字以内、举一个计数器的例子来说明，避免使用"作用域链""词法环境"这类术语。
```

### 原则三：分解复杂任务为步骤

复杂任务一次性丢给模型，它容易跳步或遗漏。把任务拆成有序步骤，让它一步一步来。

```text
差：分析这段用户反馈，给出改进建议
好：请按以下步骤处理这段用户反馈：
1. 提取用户提到的所有问题点，编号列出；
2. 对每个问题判断严重程度（高/中/低）；
3. 针对每个高/中问题给出一条可执行的改进建议；
4. 忽略情绪化的抱怨，不输出安慰性话语。
反馈：……
```

### 原则四：提供示例（Few-shot）

当口头描述说不清"我要什么样的输出"时，直接给一两个例子，比写半页规则都管用。

```text
差：把产品名翻译成英文，要好听
好：参考下面的风格翻译产品名：
输入：飞书 -> 输出：Lark
输入：钉钉 -> 输出：DingTalk
输入：石墨文档 -> 输出：
```

### 原则五：指定输出格式

需要程序消费的输出，**必须钉死格式**。否则模型一会儿带 markdown、一会儿加前言，下游解析必崩。

```text
差：列出几个常见水果的颜色
好：输出一个 JSON 数组，每个元素形如 {name: 苹果, color: 红色}，包含 5 种水果。只输出 JSON，不要 markdown 代码块，不要任何解释文字。
```

> 开发中常用的小技巧：让模型先输出 JSON 代码块标记再写内容，能显著降低格式错误率（OpenAI 最佳实践也推荐这种"结构化输出"思路）。

## 四种常见 Prompt 模式

### 模式一：Zero-shot（零样本）

不给例子，直接下指令。适合任务简单、边界清晰的场景。

```text
差：判断这句话是正面还是负面。
好：对下面这条评论进行情感分类，只能从 [正面, 负面, 中性] 中选一个词作为输出，不要解释。
评论：这个耳机电续航很猛，但戴着夹耳朵。
```

### 模式二：Few-shot（少样本）

给 2-5 个示例，让模型"照葫芦画瓢"。适合格式特殊、规则难用文字说清的任务。

```text
差：把句子转成 SQL 查询。
好：根据示例，把自然语言转成 SQL。

问：查询年龄大于 30 的用户姓名。
答：SELECT name FROM users WHERE age > 30;

问：统计每个部门的员工数量。
答：SELECT department, COUNT(*) FROM employees GROUP BY department;

问：找出价格最高的商品。
答：
```

### 模式三：Chain-of-Thought（思维链）

对于推理、数学、逻辑题，要求模型"一步一步想"。Anthropic 和 OpenAI 都证实这能显著提升复杂推理的正确率。

```text
差：小明有 5 个苹果，吃了 2 个，又买了 3 个，他有几个？
好：小明有 5 个苹果，吃了 2 个，又买了 3 个，他有几个？请一步一步推理，先写出每一步的计算，最后再给出答案。
```

模型会更倾向于输出"5 - 2 = 3，3 + 3 = 6，答案是 6"这种可追溯的过程，而不是直接吐一个可能算错的数字。

### 模式四：角色扮演

给模型设定一个身份，激活它对该领域的专业知识与表达风格。

```text
差：怎么减肥？
好：你是一名注册营养师，服务对象是一名久坐的程序员，BMI 28，无基础疾病。请为他制定一份为期 7 天的饮食计划，每天早中晚三餐，标注大致热量，语气专业但不冷漠。
```

## 常见的坑

- **模糊指令**："写得专业一点""优化一下"——专业和优化都是没有刻度的词，模型无从下手。
- **矛盾约束**：既要"详细全面"又要"500 字以内"，模型只能二选一，结果两边不讨好。
- **让模型猜**：不告诉它字数、格式、受众，指望它"应该懂"。
- **指令淹没**：Prompt 塞了十几条要求，模型会漏掉中间几条。重要约束放在末尾或开头（首因/近因效应）。
- **忽视版本差异**：不同模型对同一 Prompt 反应不同，换模型记得重测。

## 实战速查清单

写完一个 Prompt，对照这几条自检：

1. 任务能一句话说清吗？
2. 输出格式钉死了吗（字数 / 结构 / 是否要解释）？
3. 有没有矛盾的约束？
4. 复杂任务有没有拆步骤？
5. 边界模糊的地方，要不要补一个示例？

能答"是"的越多，Prompt 越可靠。

## 小结

Prompt 工程不是死记硬背口诀，而是养成"把话说清楚"的习惯。核心就一句：**别让模型猜**。把任务、上下文、约束、示例、输出格式都摆到台面上，模型的表现会稳定上一个台阶。

更重要的是：**把 Prompt 当代码**。版本化、做对比测试、迭代优化。一个反复打磨的 Prompt，是你产品里最值钱的资产之一。
